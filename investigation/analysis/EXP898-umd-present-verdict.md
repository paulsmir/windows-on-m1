# EXP898: DWM reaches native Present but not the kernel callback

## Result

Receipt-only package `30.0.898.0` did not change caps, DXGI return values, firmware, Mu, or rendering. The live DWM PID 1232 entered the native D3D10 `_Present` DDI repeatedly (bounded counters through count 32). Each sampled `AgxD3d10WindowsPresentationSubmit` returned `E_FAIL` before `AdmissionUmdSubmitPresent`/`pfnPresentCb`. Native CreateDevice received interface `0x000a0006`, version `0x0000177a`, for which the pinned WDK `IS_DXGI1_3_BASE_FUNCTIONS` predicate is false; its `DXGI_STATUS_NO_REDIRECTION` was unchanged. The EXP897 conclusion that DWM never called Present was an artifact of its normal 128-record UMD log budget. This package's uncapped, bounded receipts disprove that inference.

At original boot +277/+329 seconds, the read-only KMD DDI query showed zero Present and virtual-Present submissions and tens of thousands of non-Present submits. A later +688-second query showed one successful BLT and virtual-Present, with one additional source-address call. The available process-local UMD and adapter-wide KMD receipts do not prove that DWM initiated this later command. Explorer PID 5068 did reach `pfnPresentCb` but received `E_INVALIDARG`. Do not attribute that KMD Present to Explorer either without a cross-layer correlation receipt.

The current DCP swap 10, sequence 3, surface IOVA `0x102a0000` matched the +120/+300/+600 snapshots after its latch; each contained zero nonzero pixels out of 4,096,000, `cache_clean=0`. Original boot `2026-09-30T13:56:23.6865960Z` ran Code0/CPU8 through +770.218 seconds without an observed kernel stop. DWM disappeared after +674 seconds; Application1000 reports d3d11/dwmcore C0000005, but no new WER or kernel dump was found. Its writer is not established by the Present receipt and remains a separate hypothesis.

## Next discriminator

The native Present implementation calls `AgxWin32AsahiContextFlushForPresent` and then `AgxD3d10WindowsFlushStatus`; the current receipt only gives their combined `E_FAIL`. `ContextFlushForPresent` can fail because the context is faulted or a batch cannot be aborted, while `FlushStatus` reports a failed submission/backend/draw terminal state. The existing DWM `reject-seterror fn=Flush ... E_INVALIDARG` records do not establish which Present subcall failed. Instrument only the exact two subcall statuses and existing context/backend/batch state in one bounded UMD receipt; then reproduce the identified owning defect offline with a deterministic RED/GREEN replay before a behavior-changing package. Do not change NO_REDIRECTION, write an unnegotiated Present1 slot, or treat the DWM crash as caused by this path without writer evidence.

# EXP964 — release non-shared resource without a KM resource handle by allocation

Classification: FULL GRAPHICS behavior correction. EXP963 reproduced DWM `pfnDeallocateCb` `E_INVALIDARG` for a resource that came from `CreateResource`, is non-shared and non-primary, has a valid KMD allocation handle `0x80001140`, and has `hKMResource=0`. The current UMD always requests `D3DDDICB_DEALLOCATE.hResource=<runtime handle>` and never uses its allocation handle for this class. EXP962 found no failing KMD `DestroyAllocation` return, so the rejection lies at the runtime/handle boundary. The separate uDWM low32 pointer corruption has no proven relation to this error.

WINDOWS CONTRACT: Microsoft's `D3DDDICB_ALLOCATE` permits non-shared allocations to be associated with the device rather than a resource, and `D3DDDICB_DEALLOCATE`/`pfnDeallocateCb` permit release by `hResource=NULL`, `NumAllocations=1`, `HandleList=&hAllocation`. Microsoft notes that a distinct resource close call is needed if a KM resource object exists. We observed `hKMResource=0` for this exact non-shared class. Shared resources must retain non-null runtime `hResource` and atomic resource deallocation; primaries keep their synchronous DestroyResource path. The pinned WDK26100 defines the callback structs.

AGX/ASAHI CONTRACT: AGX GPUVA, UAT, RTKit, native batches and DCP are unchanged. m1n1/Mu expose the same hardware and ACPI contract. The Windows UMD owns the choice of runtime deallocation form; KMD owns allocation object retirement when Windows calls it.

TRANSLATION: carry the existing `ADMISSION_UMD_RETIREMENT` metadata to the UMD's deallocation callback. For `Origin=Create`, `Shared=FALSE`, `Primary=FALSE`, `KernelResource=0`, and nonzero `KernelAllocation`, request allocation-list deallocation with `hResource=NULL`. Keep resource-handle mode for every other class. A successful callback frees the retirement exactly once; a failure requeues the same record and preserves the HRESULT. Do not fake success or free the record on failure.

ATOMIC CONTRACT: changing the callback signature from runtime handle to the retirement record and selecting the `D3DDDICB_DEALLOCATE` fields are inseparable: the callback cannot choose the documented allocation-list form without the recorded `KernelAllocation`, `KernelResource`, `Shared`, `Primary` and origin. The exact coupled fields are `hResource`, `NumAllocations`, `HandleList` in one callback invocation and the queue's existing retry/free decision. No scheduler, render, power, ACPI, firmware or cap bits change.

WHAT IS STILL UNKNOWN: whether Windows accepts allocation-list deallocation for this class on J313, whether the DWM Flush errors then disappear, and whether physical pixels or the independent DWM heap corruption improve. Test the real callback with a rejecting resource-handle mock and successful allocation-list mock, plus shared/primary and failure/retry invariants. Then one short exact package experiment after durable Code28. If callback still fails, collect exact HRESULT and roll back; do not broaden the mode without new evidence.

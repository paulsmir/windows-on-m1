# EXP967: identify why DWM GPU upload cannot pass paging quiescence

WHY THIS HYPOTHESIS: EXP966 KMD transfer receipt shows DWM PID1220 UPLOAD 64KiB at VA0x4fa0000+offset0x680000 returned `STATUS_DEVICE_BUSY` at predicate62 after 3000ms, with matching request/current process and mapping generations. UMD immediately recorded `reject-copy-escape`, `reject-copy-slot` step3, `reject-batch`, and DrawIndexed `E_FAIL`. EXP965 showed the same UMD sequence; EXP964's bounded 30-minute trace did not. This rejection is closer to the failed DWM drawing than the cumulative system PTE group count.

WINDOWS CONTRACT: VidMm builds paging buffers that dxgkrnl submits on a scheduler context; build and submit need not coincide. A KMD must preserve ordering of a resource's paging transfer/fill and any later CPU upload/command that depends on the new placement. Official Microsoft GPUVA and command-buffer flow documentation describes separate page-table updates, paging operations and submissions. Current R161/EXP874 hardware and dump evidence proved an upload that raced a deferred paging transfer corrupted the GPU target and led to 0x116. Sources: https://learn.microsoft.com/en-us/windows-hardware/drivers/display/gpu-virtual-address ; https://learn.microsoft.com/en-us/windows-hardware/drivers/display/submitting-a-command-buffer ; `investigation/analysis/R161-exp874-paging-order.md`; pinned WDK DXGKARG_BUILDPAGINGBUFFER/SUBMITCOMMAND.

AGX/ASAHI CONTRACT: The UMD copy escape reads/writes a GPU-local allocation via KMD mapped CPU access while AGX jobs and paging transfers are serialized by the current m1n1/AGX backend. A late paging transfer to the same local physical region can overwrite an earlier upload, independent of GPUVA page-table validity. Asahi mmu.rs and current m1n1 hv_agx_gpuva_v5.c enforce backing/generation but cannot reorder Windows paging buffers. Mu APPL0002 remains unchanged.

TRANSLATION: R161 currently blocks *all* UPLOAD/DOWNLOAD while `PagingRecordsUnsubmitted != 0`, `CpuQueueCount != 0`, `PagingPending != 0`, or `PagingWorkersActive != 0`; it waits at most3000ms then returns predicate62. EXP967 adds only a failure-only receipt containing those four components, relevant fences and target VA/allocation at the first predicate62. It does not remove or weaken R161. If an unrelated unsubmitted record is the blocker, the functional repair must track per-allocation or physical-range dependencies and preserve the EXP874 race guard for overlapping transfers. If queued/active work is stuck, repair its owner instead of bypassing ordering.

WHAT IS STILL UNKNOWN: which quiescence component remained nonzero for the DWM failure, whether its paging record overlaps the target allocation, and whether the queue is making progress. Existing receipts do not store this snapshot. One short diagnostic hardware run is the smallest discriminator. Expected recovery: exact package rollback to GPU-visible ordinary Code28 after evidence. Do not call Code0 or a successful copy query proof of pixels.

Inspected current source: `drivers/apple-agx/render-admission/umd/src/umd_gpuva_windows.c` (copy query/upload path), `src/gpuva_g3_windows.c` predicate62 and receipt, `src/work_queue_windows.c` quiescence and unsubmitted accounting, `src/paging_windows.c` worker/notification, `src/scheduler_windows.c` queue gates; prior EXP874 hardware analysis and official Microsoft docs above. Ownership: Windows/VidMm emits and submits paging commands; KMD owns CPU queue/ordering and copy escape; UMD propagates error to DWM draw; m1n1/AGX performs native work; Mu exposes APPL0002. Smallest checkpoint is first predicate62 queue snapshot; recovery is exact package cleanup/durable preflight.

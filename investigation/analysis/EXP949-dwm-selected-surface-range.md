# EXP949: count DWM writes that resolve into the selected scanout range

WHY THIS HYPOTHESIS:
1. EXP948 correlated one DWM presented resource at GPUVA `0x1f0000` with local IPA `0x8e11a0000`; m1n1's selected DCP IOVA corresponds, under its current fixed-pool mapping, to PA `0x8e0110000`. Those addresses differ. KMD Present and VirtualPresent counts were zero, but the DWM frame probe dropped a third context, so a different composition pass might still write the selected surface.
2. The latest EXP948 FrameArm map receipt had ordinal 618 while the indexed ring kept only ordinals 0–15. Neither the first 16 nor the last sample matched the selected source, but the middle ~600 samples were not classified. A bounded counter over the entire existing FrameArm stream resolves that gap without storing hundreds of records.
3. m1n1's zero-pixel CPU snapshot says `cache_clean=0`; it cannot conclusively prove what DCP fetched. This experiment compares mapping identity, not pixel content, and does not infer DART/cache behavior from a stale CPU view.

WINDOWS CONTRACT: FULL GRAPHICS WDDM 3.0. `DXGKARG_SETVIDPNSOURCEADDRESS` identifies a primary surface by segment and segment-relative address; WDDM 2.x GPUVAs are process-specific and must be translated through their current mapping. Pinned WDK 26100 and official Microsoft GPU virtual memory/Present documentation remain the Windows ABI source. `WrittenPrimaries` for legacy PRESENT was rejected in EXP946 and stays reverted.

AGX/ASAHI CONTRACT: Asahi's Apple DCP plane describes BGRA scanout with explicit DMA address and stride. Current m1n1 `dcp_iomfb_present.c` and `hv_agx_power_mmio.c` report the latched IOVA and fixed scanout-pool-derived PA. Current Mu `J313AppleAgxAbiAdmission.asl.inc` exposes one APPL0002. None of m1n1, Mu, DCP/DART mappings, power, IRQ, UAT page tables or GPU submission changes. KMD `AdmissionGpuvaG3FrameArmEscape` already reads valid logical PTEs under the G3 lock and publishes receipts after release.

TRANSLATION: Keep the EXP948 indexed receipt. For every valid DWM FrameArm, compare the resolved local IPA with the immutable selected scanout range `[SelectedHostPhysicalAddress, SelectedHostPhysicalAddress + Stride*Height)`, requiring segment 2 and a valid writable PTE. Increment a per-adapter observation counter and include its running value plus the range size in the latest receipt. Persist a separate first/last matching receipt only if a match occurs. This changes diagnostics alone; no branch uses the count for admission, paging, render, present or display.

WHAT IS STILL UNKNOWN: Whether any observed DWM write maps into the selected scanout range. A positive count proves one DWM BO can reach it and shifts work to content/layout/cache or final composition. A zero count across hundreds of observations supports a missing bridge, but does not exclude DCP DART remapping or an unobserved non-FrameArm producer; inspect those before a behavioral fix. A single Code0 boot with read-only map/frame query is sufficient if DWM has already drawn. Preserve original evidence and roll back exact EXP949 to normal GPU-visible Code28; immutable hidden recovery only if ordinary recovery fails.

EXP948 original state/UMD/ETL was host-gated. WHAT REAL BUG OR INVARIANT WILL THIS TEST CATCH? This is a receipt-only hardware discriminator. No artificial RED test; existing G3 graph/PTE tests, pinned ARM64 zero-warning build, signature/hash/PDB gates must pass. Do not call the screen working without operator confirmation.

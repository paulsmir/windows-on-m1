# EXP906: DWM COPY_QUERY predicate53; early TDR

Package `30.0.906.0` was built from receipt-only commit `99c9e1586656167101fac19ce5e530f9cf8a6cd3`, based on the exact EXP905 behavior. R185's per-page COPY_QUERY fix was excluded. The pinned WDK ARM64 KMD and UMD build passed with zero warnings and errors; INF/SYS/UMD/CAT and PDB hashes are preregistered in `investigation/EXPERIMENTS.md`. Firmware and Mu were byte-unchanged. The first launch attempt stopped before loading firmware because the packaging helper omitted an alias; the alias was proved byte-identical to the manifest-pinned firmware before the one original Windows boot.

The original boot began `2026-09-30T21:21:27.9758850Z`, reached Code0/StartDevice stage12/status0/CPU8/SSH/DWM1244/Explorer5124, and its last live monitor sample was boot+77.213 s. m1n1 logged a guest PSCI reset. Both host-preserved ARM64 `MEMORY.DMP` and minidump headers report `0x116 VIDEO_TDR_FAILURE` with parameters `ffffd8842621f010`, `fffff802bcd39e80`, `ffffffffc0000483`, `3`. Cdb identifies the dump time as `21:22:50.378Z`, uptime **82.918 s**, process System, `dxgkrnl!TdrBugcheckOnTimeout -> DXGADAPTER::PrepareToReset`, and failure bucket `0x116_IMAGE_AppleAgxRenderAdmission.sys` at `AdmissionDdiResetFromTimeout`. Parameter 3 is `STATUS_DEVICE_HARDWARE_ERROR`; `scheduler_windows.c::AdmissionResetEngineInternal` can return that status if `AdmissionGpuvaG3PrivateReset` fails, but the dump does not establish that exact branch or the initial hung packet. Do not equate the DWM copy refusal with the TDR cause without a same-context/fence receipt.

The original periodic snapshot at `21:22:17Z` contains a DWM PID1244 `reject-copy-slot` step1 for **KernelAllocation `0xc0000a80`, canonical GPUVA `0x7d0000`, size `0x10000`**. Its escape HRESULT was `0x88760870`, with zero returned process/mapping generations. It immediately led to native `reject-batch` kind3/site `0x15a`, GPUVA `LastFailure=0xa4`, `LastDetail=0x100`, then `ResourceCopyRegion` E_FAIL. The new KMD `Wom1G3Q000004DC01` receipt independently names OS PID1244, the same allocation/VA/64 KiB, **predicate53 / `STATUS_INVALID_PARAMETER` (`C000000D`)**, graph process3, KMD context `ffffd8841e812540`, process generation1 and mapping generation4305. This is the previously missing DWM-specific correlation. The bounded per-PID receipt did not include a walk detail because the adapter-global first receipt had already claimed the walk buffer; the exact absent leaf and resident PTE state of this DWM range remain unmeasured. Current code places predicate53's 16 KiB published graph walk before full 4 KiB `ResidentPtes` provenance checks. R185's actual extracted-KMD replay independently proves that a fully resident, scattered 4 KiB local allocation is rejected by old predicate53 and accepted after using pagewise provenance. EXP906 proves DWM encountered predicate53; **it does not prove this DWM allocation satisfied R185's valid-residency preconditions or that R185 would make the query succeed**. R185 is not hardware-validated as a fix because it was not in package906.

No same-original-boot KMD Present/virtual-Present counter query completed before the reset. The saved DWM UMD logs contain no bounded `measure-present-*`/`present-callback` receipt; they show the copy rejection during a render batch. EXP905's earlier two DWM `pfnPresentCb` S_OK events and later KMD Present0 are a separate surviving scheduling question. EXP906 cannot answer whether a queued Present was waiting behind a DWM DMA/fence, nor whether a failed `SubmitCommandVirtual` belonged to that context. DCP swap9/current IOVA `0x102a0000` had only seq2 early and +15 s snapshots, both zero. The reset preceded the valid +120/+300/+600 measurements; **none of those three late snapshots exists for EXP906**. Display, SSH, DWM and CPU8 were alive to boot+77 s; no 600 s stability or nonzero scanout result can be claimed. The DWM crash/writer hypothesis remains separate.

Original periodic ETL/UMD/registry snapshot 3/3 and hidden manifest plus 14 files 15/15 were independently host size/SHA verified **before any cleanup**; aggregate `final-host-manifest.json` SHA `d7dd1e696190369a7ae57ecd56236faa8c3cd8c6d1fc2645573ab2fa837e4631` is authoritative. The original ETL was captured during the Code0 boot; the guest ETL was later reused by recovery and is not original evidence. All original/hidden dumps, logs, and PDBs remain on the host. Guest source `MEMORY.DMP` changed after recovery; its then-current 584,586,157-byte contents were independently copied and host-verified (gate SHA `169f967254dcfb848872e3b2a07340a28c863d6f928d4176df3c2604c3f5f782`) before removing that exact guest source to free C:. The inactive recovery ETL was also copied and host-verified separately. All package and diagnostic cleanup occurred only under hidden Code45 after the original and hidden gates, followed by immutable GPU-visible ordinary recovery.

The first ordinary recovery boot stalled without SSH for over five minutes. After an evidence-preserving proxy reset, freeing the changed guest dump under hidden package0 raised C: from 189 MB to 774 MB; a second immutable ordinary boot at `21:56:29Z` passed durable checks at `21:57:31Z` and `22:02:54Z`: one GPU-visible APPL0002 Code28, package/arms/SYS/UMD/service/signer/diagnostics absent, CPU8, both disks OK, USB5, RDP, autologon1/password present. Two host-verified guest EVTX duplicates were then removed. Fresh same-boot read at `22:03:19Z` found C: free `590,520,320` bytes, up from zero in hidden recovery but below the pre-EXP906 ~1.26 GB. No package was removed live Code0 and autologon was not changed.

Verdict: **confirmed DWM-specific predicate53 refusal; rejected 600 s stability and nonzero scanout for package906; unknown TDR initiating fence/context and post-callback Present scheduling.** Next perform the single-pass end-to-end Present audit in `investigation/analysis/PRESENT-PATH-AUDIT.md`, then design one same-context/fence/VA receipt for each remaining unknown. Do not ascribe the `0x116` to the DWM query solely because they occurred in the same boot.

## The atomic no-publication boundary

`shared/src/apple_agx_backend_runtime.c:213–278` checks phase/envelope, Resolve, Relocate and Flush before Run3d. Those early calls can mutate image/overlay memory, but they do not call this submission's queue publisher. The owner mismatch returns before Resolve. Run3d FALSE expressly means this fence was not accepted, clears runtime pending shadow and leaves Ready. The concrete provider `shared/src/apple_agx_g13_queue_provider.c:304–323` validates before changing state and only stages D3 addresses/fence: it publishes no queue pointer or Run message.

**RunTa FALSE is not equivalent.** `apple_agx_g13_queue_provider.c:325–434` includes both pure validation failures and queue-runtime submission failures. `apple_agx_g13_queue_runtime.c:292–393` writes/flushed prepared objects and ring entries, then publishes D3's write pointer, TA's write pointer, and both Run messages. Its `visible` boundary is the first successfully published write pointer, before the Run messages. Compute has its own first publication at `:227–278`; compute acceptance followed by render refusal is already execution, not prequeue rejection. `:210–225` attempts quiesce for visible failures. Backend subsequently marks Failed even if provider Stop succeeds, so neither QueueFailed nor backend Failed classifies publication.

The concrete Windows `AdmissionTransportPublishU32` at `backend_platform_windows.c:1726–1737` returns FALSE only before its store; after the store it barriers and returns TRUE. Thus the current provider's first failed publish can be classified as unpublished when reached from a proven clean generation. The generic callback type in `shared/include/apple_agx_g13_queue_runtime.h:60` does not itself state this no-side-effect-on-FALSE requirement. A future callback that stores and then fails would invalidate that classification.

A safe transaction therefore needs a monotonic, exact-submission disposition, conceptually `Preparing -> NeverPublishedRejected` or `Preparing -> PublicationPossible -> Submitted/Quiesced/Uncertain`. The submission identity must include context/process/scene and runtime generation, not a fence scalar or a later snapshot of Ready/Created alone. Publication and cancellation must share one owner/claim: after a cancellation claim the worker must not publish; after any successful/potentially side-effecting pointer publication the never-published path must be permanently unavailable. Do not move BeginJob after publication to obtain easier rollback: the lease is required before firmware can access process memory.

For a proven never-published rejection, a distinct PASSIVE abort helper can legitimately do JOB_END then RELEASE without setting GpuDone, Reported, LastCompletedFence or success receipts. It must verify the exact ActiveProcess/ActiveFence/scene/generation and existing lease, and retain quarantine on either broker failure. `GraphEndJob:652–675` already distinguishes JOB_END success from RELEASE failure through JobInFlight/LeaseToken/Uncertain; callers must not erase that partial state. Image/overlay ownership still needs an abort release, and OS fence disposition is a separate obligation.

## Supported WDDM dispositions

Microsoft sources were opened in English on 2026-09-28.

1. **Do not emit DMA_FAULTED.** The current [DXGK_INTERRUPT_TYPE](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmddi/ne-d3dkmddi-_dxgk_interrupt_type) contract says “Reserved for system use. Do not use in your driver.” Existing `paging_windows.c:196–229` does emit this on paging error; that is a separate source-contract issue, not a precedent to copy into render rejection. DMA_COMPLETED denotes completion; DMA_PREEMPTED requires an actual preemption request and the last truly completed fence.
2. **Prefer synchronous malformed-input rejection where possible.** [SubmitCommandVirtual](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmddi/nc-d3dkmddi-dxgkddi_submitcommandvirtual) permits STATUS_INVALID_PARAMETER for malformed DMA/private data, puts the calling device into error, and prescribes retirement only after earlier packets finish. Other errors bugcheck. This route must run while the DDI is still executing; it does not classify an internal owner mismatch, broker failure or resource failure as malformed user data. Physical [SubmitCommand](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmddi/nc-d3dkmddi-dxgkddi_submitcommand) errors bugcheck.
3. **Truthful requested preemption is possible without claiming execution.** On an actual [PreemptCommand](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmddi/nc-d3dkmddi-dxgkddi_preemptcommand), a definitively nonpublished packet can be canceled and publication prevented; acknowledge only the supplied preemption fence, with the old actual completed fence, via synchronized interrupt notification/DPC. This is a design inference from the cancellation and notification contracts, not a tested Windows behavior in this tree. It needs a new rejected-active scheduler transition; ObserveBoundaryCompletion cannot be reused. It also needs policy for deterministic rejection on resubmission—otherwise it can produce endless preempt/retry rather than a device error.
4. **Device error is not an invented generic KMD callback.** [DMA_PAGE_FAULTED notification data](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmddi/ns-d3dkmddi-_dxgkargcb_notify_interrupt_data) supports GPU errors with a null fault VA for a non-address cause. [General error codes](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmdt/ne-d3dkmdt-_dxgk_general_error_code) describe GPU page fault/invalid instruction; [fault flags](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmdt/ne-d3dkmdt-_dxgk_page_fault_flags) prescribe reset needs and completed-fence accounting. This is not evidence that a host-side owner/validation rejection before GPU encounter may be relabeled a GPU fault. A vendor error code alone does not establish that permission. Do not fabricate a fault address, invalid instruction or engine timeout. [SetErrorCb](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3d10umddi/nc-d3d10umddi-pfnd3d10ddi_seterror_cb) is a UMD runtime error return mechanism, not the KMD's accepted-fence retirement callback.
5. **Reset remains a valid recovery framework only with full guarantees.** [ResetEngine](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmddi/nc-d3dkmddi-dxgkddi_resetengine) success requires an empty affected queue and readiness for new packets. [ResetFromTimeout](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmddi/nc-d3dkmddi-dxgkddi_resetfromtimeout) must stop all GPU memory access; failure bugchecks. [TDR rules](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/tdr-changes-in-windows-8) require real aborted/completed fence accounting and retain adapter-reset duties even with per-engine support. Nonpublication proof can support an abort without stopping this job, but it does not establish global hardware/firmware health after a heartbeat or transport failure. Keep uncertainty fail-closed.
6. [CancelCommand](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmddi/nc-d3dkmddi-dxgkddi_cancelcommand) is an OS-invoked cleanup DDI for packets still in the scheduler's software queue when a device errors, gated by CancelCommandAware. It is not an outbound notification to abandon a packet already accepted into this driver's worker queue.

## Required races and regression boundaries before implementation

* Serialize worker publication versus preemption, reset and stopping. Current activation releases SchedulerLock before BeginJob/submit; PrivateReset can acquire the G3 mutex and quarantine Started before runtime reset drains workers. A new abort must not race that quarantine or permit publication after lease release.
* Preserve lock order and IRQL: broker/scene work is PASSIVE under the G3 fast mutex; scheduler/packet transitions use spin locks. The current submit path takes G3 mutex then SchedulerLock. Do not take the fast mutex while holding SchedulerLock. Use a claim/token handshake and retained references across the PASSIVE portion.
* Prevent duplicate JOB_END/RELEASE and duplicate notification under worker/reset/preempt overlap. Revalidate scene/process/fence/generation after any unlocked interval. No stale pointer or recycled fence may abort a newer packet.
* Keep the OS fence debt explicit until preemption/reset/device-error semantics discharge it. Do not clear ActiveFence/DispatchedFence and allow later CPU/paging or render completion to jump over an unreported rejection. Preserve preemption cutoff and the actual last completed fence, including wraparound. A synchronized notification failure must remain pending/faulted, not silently retire.
* Retain context/image/private-scene ownership through the transaction; handle a simultaneous release request, submitting scene, process/context destruction, and partial broker failure. Restore/release materialized overlays separately from queue ownership.
* Host fault injection must cover: early envelope/Resolve/Relocate/Flush failure; Run3d refusal; RunTa validation refusal; prepared/ring flush failure; first/second pointer publication; first/second Run send failure; compute accepted before render failure; JOB_END failure; RELEASE failure; and each preemption/reset/stop interleaving. Assert notification payloads, unchanged success counters/stamps, no future publisher after cancellation, and quarantine for every ambiguous publication case. The real worker-to-backend envelope should be exercised, not just a model with the same branch logic.

No regression was added or run because no implementation is proposed for this pass. The smallest next offline checkpoint is an exact never-published disposition test plus an abort transaction that demonstrably leaves successful-completion state unchanged and cannot race publication. A later hardware checkpoint, if separately authorized, would inject one pre-publication refusal and verify the exact lease/scene/scheduler/OS disposition and recovery; it must be preregistered and must not reuse EXP865's in-flight220 as that case. Ordinary GPU-visible Code28 remains the saved recovery state. Existing active-private quarantine must remain for accepted or uncertain work.

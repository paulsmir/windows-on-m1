# EXP968: retry a late paging-quiescence race before DWM CPU copy

WHY THIS HYPOTHESIS: EXP967 captured DWM PID1220 DOWNLOAD64KiB returning KMD predicate62/`STATUS_DEVICE_BUSY` with `WaitMilliseconds=0`. `PagingRecordsUnsubmitted=7`, while submitted CPU queue, paging pending, active worker/DPC, scheduler fault and native process activity were all zero. Request/current GPUVA generations matched. UMD then rejected the copy slot and batch. In source, the first `AdmissionPagingQuiescent` test can return true, new BuildPagingBuffer records can be encoded before the later predicate62 test, and the later test returns BUSY immediately; this is the exact offline RED replay. EXP966/965 had the same DWM copy-failure class, but their wait duration was unmeasured. Do not repeat the incorrect earlier inference that EXP966 waited three seconds.

WINDOWS CONTRACT: VidMm separates BuildPagingBuffer from SubmitCommand, and may build paging records concurrently with a UMD escape. The KMD must prevent a CPU upload/download from racing a relevant later fill/transfer. Microsoft's DXGKARG_BUILDPAGINGBUFFER and Submitting a Command Buffer documentation define these stages. R161/EXP874 proved by hardware 0x116 that copying into new placement before delayed paging transfer completed is unsafe. Sources: https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmddi/ns-d3dkmddi-_dxgkarg_buildpagingbuffer ; https://learn.microsoft.com/en-us/windows-hardware/drivers/display/submitting-a-command-buffer ; `investigation/analysis/R161-exp874-paging-order.md`; pinned WDK 26100 headers.

AGX/ASAHI CONTRACT: KMD copy escape reads/writes GPU-local backing after AGX/UAT ownership and GPUVA mapping validation. The serialized node0 paging worker may later fill/transfer the same physical bytes; neither Asahi UAT nor m1n1 can infer the Windows command order. Current m1n1 `hv_agx_gpuva_v5.c`, Mu generated APPL0002 ACPI and AGX power/IRQ contracts are unchanged.

TRANSLATION: Keep `AdmissionPagingQuiescent` and all existing owner/context/allocation/range checks. If new paging work appears between the initial wait and the final guard, release G3 state lock, delay1ms and retry the entire owner/context validation, using the same cumulative 3000ms ceiling. The copy still executes only after final quiescence and full range validation. This fixes a measured immediate refusal without weakening R161. The remaining post-check/build concurrency window exists in the current implementation and is not claimed solved; a later per-allocation dependency design may still be needed. RED replay flips paging state after the initial successful check; old code rejects predicate62/STATUS_DEVICE_BUSY, new code waits for the simulated drain and succeeds. The existing no-drain R161 replay must still return BUSY after3000 delays.

WHAT IS STILL UNKNOWN: whether the seven built records in the Air boot submit soon enough for bounded retry to help, whether they target this DWM allocation, and whether the physical desktop becomes correct after copy succeeds. One hardware run with unchanged m1n1/Mu/UMD and only this KMD retry distinguishes the first question; collect DWM copy/DrawIndexed and operator pixels quickly, then exact rollback unless physical success is proven. If 3000ms still expires, do not lengthen the timer blindly; track record type/allocation/range before a per-target scheduling fix.

# M1 survey: a conditional 1 GiB ramdisk window

Date: 2026-10-12. Read-only survey for roadmap step M1 (reserve the ramdisk window
0x860000000-0x8A0000000 only when the boot carries a ramdisk; otherwise give the RAM to
Windows) while keeping WinPE/ANS ramdisk boots. Prefixes: `E` =
`/Users/pavel/public_windows/.local/experiments`, `G` = `.local/tandem/gpu-pipeline`,
`A` = `.worktrees/ans-native`.

## Headline

- M1 needs m1n1 and Mu to change together. Mu alone gives Windows the window while m1n1
  98cdabae still refuses every GPU backing page in it (likely an unrecoverable 0x116).
- Only the launcher (`run_uefi.py`) knows a ramdisk is present, and it never clears the header
  on a boot without one.
- No evidence that a stale header survives a SoC reboot, but reset-free relaunch paths exist.

## 3. Ramdisk detection today

- Header (`BootRamdiskHelperDxe.h:38-45`): "ASIRAMDK", UINT64 Size, payload at +0x1000.
  `BootRamdiskHelperDxe.c` checks the PCD, the magic and the size and registers the disk in
  place, else falls back to the FV image. PEI never reads the header.
- Writers: `run_uefi.py:306-325` and `A/run_uefi.py:369-388`, only with `--ramdisk` (payload
  first, header last). Nothing ever clears the header.
- ANS: the header ABI lives in `A/mu/.../PreloadedRamdisk.h`; `AppleAnsBootSource.h` reads it
  for the autoboot gates; ans-native's PEI still reserves unconditionally; ANS001 pins m1n1,
  Mu, WinPE and layout hashes and forbids ramdisk overrides.
- Stale headers: every ramdisk-to-normal transition in the ledger printed "no preloaded RAMDisk
  at 0x860000000" (EXP335-337, EXP343-344, EXP347-348); EXP226 shows platform state survives a
  UART reset and only `p.reboot()` cleared it. Reset-free relaunch paths exist (`run-windows.sh
  --reuse-proxy`, chainload).

## 4. m1n1

- `translate_guest` refuses GPU backings in the window so GPU DMA cannot reach the WinPE or
  ANS boot medium (m1n1 `9cf6c9d9`, CHG-20260905-474-BACKING); `local_reserve_translate` keeps
  the 1 GiB local reserve off it; `excluded[0]` and `hv_autonomous_runtime.c:228` are layout
  invariants that do not move with M1.
- m1n1 cannot know today that a ramdisk was loaded: the launch descriptor has eight region
  kinds and none for a ramdisk, `devices.flags` is 0, and EL2 must not trust a header in guest
  RAM. Channels: a ramdisk region kind in the descriptor (published before `hv.init`), or a
  `devices.flags` bit.

## Change set the survey recommends

- The launcher decides. `run_uefi.py`: validate the image before the descriptor publish; with
  `--ramdisk` add a descriptor region of a new kind `HV_CONTRACT_REGION_RAMDISK`; without it
  zero the header page (optionally clean it from the cache: PEI reads it with the MMU off).
- Mu owns the OS memory map: a shared predicate (magic, size bounds, overflow) in a
  `PreloadedRamdisk.h`; `MemoryInitPeiLib.c` reserves the window only when it holds and
  publishes a GUID HOB with the decision; `BootRamdiskHelperDxe` (and later the ANS gates)
  consume the HOB; the local-reserve exclusion stays unconditional.
- m1n1 owns EL2 DMA: a new region kind in `hv_launch_contract.h`; `hv_agx_retained_backing.c`
  accepts it (the overlap loop then denies it); drop the unconditional
  `J313_AUTONOMOUS_LAYOUT.ramdisk_*` exclusions; leave the layout invariants alone.
- No change to the layout JSON, PCDs, generated files or the ANS layout hash. A smaller-ABI
  alternative is a `devices.flags` bit (an old m1n1 ignores it and keeps the exclusion).
- Rebuild and re-hash: m1n1 (the exact 98cdabae make line, new build info), Mu (EXP856 flags,
  check the AML matches `3bdb28ed`), `run_uefi.py`, the per-experiment files. The KMD and
  package are unaffected.
- Checkpoints: a normal boot prints no "reserving preloaded RAMDisk window", keeps `regions=8`
  and gives Windows exactly 0x40000000 more RAM; a ramdisk boot prints the reserve line,
  "preloaded RAMDisk at 0x860001000" and `regions=9`.

## Risks

1. Mu without m1n1 regresses the GPU (GPU backings in the window fail `translate_guest`).
2. Old m1n1 with a new `run_uefi.py --ramdisk`: an unknown region kind denies every page and
   the local reserve fails (fatal in PEI with RESERVE_V2 Mu); recovery and WinPE use the main
   checkout's `run_uefi.py` and are not exposed.
3. The GPU-hidden recovery runs this worktree's `run_uefi.py`/proxyclient with legacy
   m1n1-exp377: dry-run it and exercise the legacy descriptor path.
4. WinPE/ANS: unchanged with a header; ANS001 is sealed on its own hashes; a rebase must port
   M1 into `A/mu` and `A/run_uefi.py` and reseal.
5. Recovery profiles keep the old Mu (1 GiB less RAM after recovery; benign with restarts).
6. A launcher that writes the header without the descriptor region leaves Mu reserving while
   m1n1 allows GPU access: every launcher must change together.
7. The stale `manifest.json` m1n1 fields and hard-coded ledger literals misreport the m1n1
   identity until fixed.

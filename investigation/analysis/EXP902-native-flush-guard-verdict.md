Thus the first fault is **specifically the generated flush guard's `!batch->draws` operand rejecting an initialized VDM clear-only batch**, not preexisting fault, missing BO, uninitialized state, shader failure, or a different process/context.

Exact Windows source has three coupled clear-only gates. `native-asahi-batch-lifecycle.py` generates `agx_flush_batch` to fault on zero draws; `agx_win32_gpuva_batch.c::AgxWin32AsahiBatchFinish` refuses zero draws; `agx_win32_asahi_scene.c::AgxWin32AsahiContextFlushForPresent` flushes only a batch with draws and otherwise aborts it. The pinned upstream Asahi/Mesa flush admits initialized VDM clear work and resets only a batch with no CDM/VDM work. R182 commit `274258cef833bc0b7ab24b7eeaf6031510a15bd5` changes the three predicates as one atomic clear-only render invariant, keeping no-work, missing VDM, compute-only and failed capsule paths fail-closed.

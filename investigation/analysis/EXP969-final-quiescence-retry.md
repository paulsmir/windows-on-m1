# EXP969: retry the second final paging-quiescence failure

WHY THIS HYPOTHESIS: EXP968 was intended to retry late paging work but DWM still received predicate62/`STATUS_DEVICE_BUSY` with `WaitMilliseconds=0`, `RecordsUnsubmitted=13`, and queued/pending/active paging all zero. The same UMD sequence ended in DrawIndexed `E_FAIL`. The current code independently invokes `AdmissionPagingQuiescent` in the retry condition and again in the predicate62 macro: if the first final call returns true and a paging buffer is built before the second, the macro fails immediately without re-entering the retry. A deterministic replay that flips paging state at this second final check is RED on EXP968 and GREEN after EXP969's change.

WINDOWS CONTRACT: VidMm may build paging buffers concurrently with a UMD escape; BuildPagingBuffer and SubmitCommand are separate DDIs. An upload/download cannot ignore relevant delayed fill/transfer, as R161/EXP874 hardware demonstrated by 0x116 after an unguarded copy. Official Microsoft references: https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmddi/ns-d3dkmddi-_dxgkarg_buildpagingbuffer ; https://learn.microsoft.com/en-us/windows-hardware/drivers/display/submitting-a-command-buffer . Pinned WDK 26100 and R161 analysis supply the precise implementation contract.

AGX/ASAHI CONTRACT: AGX GPU-local backing and UAT mapping do not encode Windows paging-submit order. The KMD CPU copy must wait for the corresponding paging worker before using the local physical bytes; m1n1 `hv_agx_gpuva_v5.c`, Asahi `mmu.rs`, and Mu APPL0002 remain unchanged.

TRANSLATION: Keep the original 3000ms cumulative wait, G3 process/context/allocation/range validation and all status returns. Evaluate both existing final quiescence samples; if either sees new work, release G3 lock and repeat the full validation after1ms. Only after both samples are true can copy proceed. This removes an immediate refusal between the two existing final checks. It does not claim to serialize a new paging build that begins after the last sample; that residual Windows/KMD ordering question remains for a later per-allocation synchronization design if hardware still fails. RED replay flips state on second final call; EXP968 returns BUSY at WaitMs0. GREEN replay waits for simulated drain and succeeds for 16/64 page profiles, while the prior no-drain R161 test remains BUSY after3000 delays.

WHAT IS STILL UNKNOWN: whether the Air's late records drain within the bounded retry, whether an even later build can still race the copy, and whether physical desktop pixels become correct. One hash-verified hardware run is needed to measure copy/batch failures and operator panel. If predicate62 persists at WaitMs3000, determine whether unsubmitted records overlap target allocation before altering R161. If WaitMs0 persists, inspect the remaining post-check synchronization window. Do not call Code0/DWM lifetime stable pixels.

Inspected source: `gpuva_g3_windows.c` copy escape, `work_queue_windows.c` quiescence/record accounting, `paging_windows.c` worker, `umd_gpuva_windows.c` failure propagation; replay sources in `tests/g3_r145_copy_cases.c`, `g3_vidmm_replay.py`, `g3_vidmm_replay_shim.h`; official Microsoft and Asahi/m1n1/Mu sources above. Ownership: Windows VidMm builds/submits paging; KMD owns copy and queue-order guard; UMD propagates result to DWM; m1n1/AGX executes hardware work; Mu exposes resources. Recovery exact package cleanup in ordinary Code43 and durable Code28, hidden only if ordinary unavailable.

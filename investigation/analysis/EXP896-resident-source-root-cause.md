# EXP896 source residency: pinned-dump finding

Exact package896 KMD PDB `d093a59dbec55f89f6a876c0b8338d9eec051a23402af3586a5969b390f2c6fb` against host-verified `MEMORY.DMP` `8c544f7e20001a6a8666ec30f2fdcc09c0866ab92cc145768db385879d70f0a3` resolves the Present worker source GPUVA `0x1050000`, 2560×1600×4 bytes (`0xFA0000`), destination GPUVA `0xB0000`. The process root IPA `0x9D6130000` matches the context, `Graph.Uncertain=0`, and context/process poison flags are clear. A fixed graph walk finds all 1,000 destination 16 KiB leaves published writable but only 158/1,000 source leaves published; the first missing source leaf is GPUVA `0x1054000`.

The source **is not evicted or unmapped**. The leaf table shadow at broker IPA `0x9D6140000` has `ResidentPtes=0xFFFFA5855B802000` and `LogicalPtes=0xFFFFA5855BB02000`. Dumping all 4,000 source 4 KiB `ResidentPtes` shows `VALID|WRITE` in all 4,000, `SegmentId=0` in all, nonzero guest IPA in all, the same VidMM allocation pointer `0xFFFFA5855BAC4EA0` in all, and exact allocation offsets `0,0x1000,...,0xF9F000`. The first unpublished 16 KiB group has valid resident PTEs at IPA `0x975FD0000`, `0x975FD1000`, **`0x975FD3000`**, `0x975FD4000`: the third 4 KiB system page is physically noncontiguous. `gpuva_g3_paging_windows.c` publishes a 16 KiB AGX graph leaf only when all four 4 KiB VidMM PTEs are valid, same segment/flags and physically contiguous; it intentionally preserves resident logical mappings when a system group is CPU-only. Hence the software Present copy's source `GraphContainsRangeAccess`/`GraphTranslateVa` is the wrong representation for a CPU-readable VidMM-resident system allocation. This is a representation error, not a broker capacity leak or an unmap race in the observed dump.

[Microsoft's GPUVA documentation](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/gpu-virtual-address) states that system memory is allocated at 4 KiB granularity, whereas the current AGX UAT leaf publishes 16 KiB contiguous groups. [Residency overview](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/residency-overview) distinguishes GPUVA command residency from legacy allocation lists. The KMD's own `AdmissionG3CopyPte` already reads `ResidentPtes` under the process state lock for other CPU-copy services; `LogicalPtes` deliberately excludes 64 KiB CPU-envelope updates. The minimal owning fix is to prevalidate and read **source** 4 KiB resident PTEs (same allocation/offset and valid provenance) while retaining published-graph 16 KiB validation for the **destination** local primary, with the same state lock held across preflight and copy. It must not add missing leaves to the AGX UAT graph merely to satisfy a CPU copy. A deterministic RED replay must include physically scattered source pages whose resident PTEs are valid but no 16 KiB graph leaf exists.

Separate contracts still need verification before hardware: a missing resident source page must not be reported with `DXGK_INTERRUPT_DMA_FAULTED`, which [Microsoft reserves for system use](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmddi/ne-d3dkmddi-_dxgk_interrupt_type); a legal failure must not be mistaken for successful completion. The current KMD also replaces the caller's BLT rectangles with full screen for matching surface descriptions, contrary to the [DxgkDdiPresent rectangle/multipass contract](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmddi/nc-d3dkmddi-dxgkddi_present). These are separate from the proven 4 KiB CPU-source translation defect; do not group independent behavior changes in one hardware experiment without an explicit atomic-contract rationale.

# D3D12 A1: offline ABI gate

Scope: WDK 10.0.26100 `d3d12umddi.h`, SHA-256 `d338e00bbd079cfed42434b5bd8cb9c658238cfe22747fb7d3b7cff3a3cabc28`. This gate has no hardware or runtime result. The current boundary is native D3D12 admission; no AGX work is owned by this change. The pinned header stays outside the repository.

## Sources and negotiation

* Header lines 41–56 define major 12, minor 2, build 8, and alias the base token as `D3D12DDI_SUPPORTED_0003`. Lines 3183–3187 introduce R1/0010; lines 12244–12248 introduce R8/0100. These are declarations of possible interfaces, not evidence of 26100 runtime acceptance.
* Header lines 2674–2694 define `D3D12DDI_ADAPTERFUNCS` (8 entries) and `D3D12DDIARG_OPENADAPTER` with runtime handle, driver handle, callbacks, and output table. The [Microsoft OpenAdapter callback page](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3d12umddi/nc-d3d12umddi-pfnd3d12ddi_openadapter) says the UMD should query KMD hardware capabilities before device creation. The skeleton has no such query and therefore refuses device creation.
* Header lines 2608–2620 give `GetSupportedVersions` and `GetCaps` signatures. Lines 2488–2516 enumerate table types; lines 2517–2528 define optional-table enumeration and `FillDDITable`. The adapter also contains private-size, close, create, and destroy entries (2674–2684). This skeleton answers only the version count/list, logs and rejects caps and device creation, and fills each adapter slot. `FillDDITable` is fail closed; no device, list, or queue is made.
* Header lines 2655–2672 define `CreateDevice` arguments, including interface, runtime version, driver storage, and core-layer callbacks. Lines 2605–2606 define `pfnSetErrorCb`; 2584–2585 define `pfnSetCommandListErrorCb`. A rejected CreateDevice reports through SetErrorCb when provided. No command-list handle exists, so command-list error reporting is not exercised.
* For 0003, header lines 3060–3176 define 89 core-device function fields; 2999–3057 define 51 graphics command-list fields; 2729–2738 define seven queue fields, two of them reserved `void*` slots. The source assigns all callable slots to typed fail-closed functions and the reserved slots to null. These tables are coverage scaffolding: the adapter's rejection prevents the runtime from receiving them. No false claim of a usable D3D12 device is made.

**Version decision.** Advertise only 0003 as the smallest token defined by this pinned header. **HYPOTHESIS:** Windows 11 build 26100 still negotiates 0003. Neither the header nor the Microsoft DDI index states its minimum accepted runtime version. This cannot be called the *lowest accepted version* without an instrumented 26100 runtime observation. The first hardware checkpoint below distinguishes acceptance from rejection. Do not advance to 0010 or 0100 based solely on their presence in the header.

## Caps and feature contract

Header lines 2922–2935 say the 3D pipeline query reports the maximum level and define `D3D12DDI_3DPIPELINELEVEL_11_0 = 10`. Header lines 694–699 define binding tier 1; lines 740–750 put it in `D3D12DDI_D3D12_OPTIONS_DATA_0003`. Header lines 2906–2915 define shader caps. The [Microsoft hardware feature level table](https://learn.microsoft.com/en-us/windows/win32/direct3d12/hardware-feature-levels) says D3D12 drivers are FL 11_0 or higher and lists tier 1 as permissible at FL 11_0. The [hardware tiers table](https://learn.microsoft.com/en-us/windows/win32/direct3d12/hardware-support) specifies tier-1 descriptor and per-stage limits. **Planned minimum, not advertised:** pipeline 11_0, resource binding tier 1, heap tier 1, no conservative rasterization, no tiled resources, no cross-node sharing, no ROVs, no optional shader precision or double support unless separately proven. An FL 11_0 claim also needs all baseline shaders, formats, UAVs, texture and multisample operations, descriptors, resources, lists, queues, fences and residency. This skeleton returns `E_NOTIMPL` for every caps query, including those baseline caps, so it cannot be admitted as FL 11_0.

## Contracts and ownership

| Layer | Current contract | A1 ownership |
|---|---|---|
| WINDOWS CONTRACT | `OpenAdapter12` supplies adapter functions; version negotiation and caps precede `CreateDevice`; runtime requests versioned device/list/queue tables. See header citations above and [Microsoft D3D12 UMD DDI index](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3d12umddi/). | ABI shapes, explicit rejection and diagnostics only. |
| AGX CONTRACT | Existing D3D11 Mesa frontend and Windows winsys are the candidate backend; DXBC-to-NIR is the candidate SM 5.1 shader path. See `drivers/apple-agx/mesa/d3d11/agx_d3d11_ddi.cpp` and `drivers/apple-agx/mesa/dxbc`. | No initialization, runtime operation, IRQ, DMA, power, or recovery. |
| TRANSLATION | Future front end owns D3D12 object lifetimes, explicit state, descriptors, heaps, lists, queues and fences; the winsys/AGX backend owns execution. | No translation yet. |
| WHAT IS STILL UNKNOWN | Minimum accepted 26100 interface, exact package registration for D3D12, runtime caps query order, SM5.1 DXBC coverage, residency and fence mapping. | Measure before any feature claim. |

Microsoft's [UMD loading page](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/loading-a-user-mode-display-driver) names `UserModeDriverName`; its [D3D11 registration page](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/enabling-support-for-the-direct3d-version-11-ddi) also names `InstalledDisplayDrivers` and describes version-order slots. No D3D12-specific value name or slot was proven from these pages. Existing `UserModeDriverNameWow` is used in this repository's UMD32 build path, but no INF/package changes are made in A1.

## Smallest falsifiable checkpoint and recovery

After a separately approved, hash-recorded package and recovery image, load the D3D12 runtime with only this 0003 ABI gate and log whether `OpenAdapter12`, `GetSupportedVersions`, `GetCaps`, and `CreateDevice` are called, their arguments, and HRESULTs. The expected result is deterministic refusal before any GPU access. If 26100 rejects 0003 before the adapter callback, compare one newer version token in a separate experiment. Recover with the previously hardware-validated D3D11 image and exact package cleanup. No hardware experiment was run here.

## A2 packaging and first runtime checkpoint (offline implementation)

The ARM64 `AppleAgxRenderAdmissionUmd.vcxproj` now compiles the gate in the same DLL as the existing UMD and its `.def` exports `OpenAdapter12` beside `OpenAdapter10_2`. The INF's existing `UserModeDriverName` points at this DLL. `APPLE_AGX_D3D12=1` must be present in the **calling process** before OpenAdapter12 supplies any table; other processes get `E_NOTIMPL`. No INF, KMD, firmware, power, DMA, interrupt, or recovery behavior changes. The UMD's existing diagnostic logger must be configured for receipts; its quota and trace mode determine what is retained.

For the separately approved hardware checkpoint, build and hash this DLL/package and `windows/icd/agx_d3d12_probe.c` for ARM64, linking the probe with `d3d12.lib dxgi.lib dxguid.lib`. Run only the probe with `APPLE_AGX_D3D12=1`; it enumerates DXGI adapters, selects vendor `0x4c505041`, calls `D3D12CreateDevice` at FL 11_0, and prints the HRESULT. Expected receipts: `d3d12-open-adapter`, `d3d12-versions` (count and array presence), `d3d12-caps` (type, data size, E_NOTIMPL), `d3d12-create-device` (interface, runtime version, E_NOTIMPL) if reached, and `d3d12-close-adapter` if called. The expected CreateDevice outcome is failure before GPU access; the actual callback sequence and HRESULT are the checkpoint. Recover by collecting trace and stdout, removing that exact package, then restoring the previously validated D3D11 artifact and ordinary recovery state. No hardware run was performed for A2.

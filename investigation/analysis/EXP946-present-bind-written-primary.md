# EXP946: report GPU writes to PRESENT-bound swapchain backbuffers

WHY THIS HYPOTHESIS:
1. In 945 DWM Present source allocation `0x40003500` had `WrittenPrimary=0`; the same allocation was the first written BO in a successful `SubmitCommand` with `NumPrimaries=0`. SDK displayable surfaces were correctly reported as one primary in 944, so the missing classification is specific to DWM's backbuffer path.
2. Microsoft `D3DDDICB_SUBMITCOMMAND` explicitly includes both primaries and swapchain backbuffers written by the submitted commands. Microsoft `D3D10DDIARG_CREATERESOURCE` permits `D3D10_DDI_BIND_PRESENT` with `pPrimaryDesc=NULL`, and says this is a copy-style present resource. The current `AdmissionUmdDescribePrimary` admits exactly that shape, but 944's `resourceData.Flags` ignores `BindFlags.PRESENT` when the primary descriptor and DISPLAYABLE_SURFACE misc flag are absent.
3. The existing real UMD contract fixture `create_resource(..., Primary=FALSE)` deliberately sets `BindFlags=PRESENT`. Its `WrittenPrimary` marker is currently false. This is an offline-reproducible wrong classification, independent of any DCP or AGX register behavior.

WINDOWS CONTRACT: FULL GRAPHICS WDDM 3.0, pinned WDK 26100. `D3DDDICB_SUBMITCOMMAND.NumPrimaries/WrittenPrimaries` lists every primary and swapchain backbuffer actually written by the GPU, not only textures carrying the newer `D3DWDDM2_0DDI_RESOURCE_MISC_DISPLAYABLE_SURFACE` flag. `D3D10DDIARG_CREATERESOURCE.BindFlags` has `D3D10_DDI_BIND_PRESENT`; `pPrimaryDesc` may be NULL on such a resource. `D3DDDICB_ALLOCATE` per-resource metadata is returned in `D3D10DDIARG_OPENRESOURCE`. Official Microsoft DDI references for those three structures and resource bind flags were inspected 2026-10-03.

AGX/ASAHI CONTRACT: The existing native AGX batch passes exact written BO tokens to the UMD GPUVA layer; UAT mappings, RTKit queue, render commands and fence completion do not change. Asahi `drivers/gpu/drm/apple/plane.c` uses explicit linear BGRA stride and DMA address for DCP; current m1n1 `src/dcp_iomfb_present.c` and `src/hv_agx_power_mmio.c` expose the stable J313 DCP surface. Mu `J313AppleAgxAbiAdmission.asl.inc` exposes one APPL0002. All firmware, platform and scanout paths stay byte-identical to 945.

TRANSLATION: In the UMD `CreateResource` path, mark per-resource metadata as `WrittenPrimary` when `BindFlags` includes `D3D10_DDI_BIND_PRESENT`, in addition to the existing primary descriptor and DISPLAYABLE_SURFACE conditions. The existing `OpenResource` metadata propagation and `AgxWin32GpuvaSubmit` handle list use that marker. Staging and ordinary shared BGRA with only RENDER_TARGET|SHADER_RESOURCE remain unmarked. No KMD, memory, queue, scheduler, VidPN, power or DCP change.

WHAT IS STILL UNKNOWN: Whether the DWM resource on the next boot follows this PRESENT-bound CreateResource path and consequently reports its allocation in `WrittenPrimaries`; whether dxgkrnl/KMD presentation or the physical image then advances. The same bounded windowed SDK probe and DWM receipts distinguish these outcomes. One hardware run only after exact945 cleanup and durable normal Code28.

WHAT REAL BUG OR INVARIANT WILL THIS TEST CATCH? A PRESENT-bound resource with `pPrimaryDesc=NULL` must retain a written-backbuffer marker through `CreateResource`. The existing real UMD callback fixture can reproduce the old false marker, so add RED before the one-condition fix and require GREEN plus the existing suite, pinned ARM64 WDK build, signatures, hashes and PDB match. Recovery remains the immutable GPU-visible 377/392 profile; emergency hidden Mu385 only if that cannot boot. The result is not a stable-screen claim without physical confirmation.

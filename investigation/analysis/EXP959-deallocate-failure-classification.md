# EXP959 — classify the deferred deallocation failure

## Evidence and decision
EXP958D full DWM dump (`.local/experiments/EXP958-mpo3-single-plane/evidence/full-dwm/dwm.exe.5552.dmp`, SHA-256 `0f97968eafd569ee12bb00f284fcdbc0fb2a359f8daca7f00126315317c27a6c`) shows two truncated `uDWM` vtable pointers in committed DWM heap. The same PID's UMD trace records `Flush` stage 3 `E_INVALIDARG` before device loss and a later teardown AV. The vtable writer is unknown; the Flush error is a preceding contract failure and the nearest instrumentable boundary. Do not treat either as the cause of the other without evidence.

## Primary sources and observed contract
- Live: EXP958 `umd-postcrash.log` PID5552, `dwm-cdb.txt`, `full-dwm/cdb-analyze.txt`, `cdb-heap2.txt`, and package958 source hashes in the ledger.
- Asahi/Mesa implementation: `drivers/apple-agx/mesa/winsys/agx_d3d10_windows.cpp` `AgxD3d10WindowsFlushDeferredResources`; its native batch/BO retirement is separate from Windows resource handles. Earlier Asahi DCP observation is recorded in `investigation/analysis/EXP949-dwm-selected-surface-range.md`; no AGX register or DART behavior changes here.
- m1n1: `m1n1_windows/src/hv_agx_power_mmio.c`, `m1n1_windows/src/dcp_iomfb_present.c`; full-owner DCP and broker remain fixed at exp954. Mu: `mu/Platform/MacBookAirMid2020Pkg/AcpiTables/J313AppleAgxAbiAdmission.asl.inc` exposes APPL0002 and local reserve; firmware remains r143. Neither layer owns `pfnDeallocateCb`.
- Windows: pinned WDK 26100 `D3DDDICB_DEALLOCATE` and official Microsoft [resource creation/destruction](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/handling-resource-creation-and-destruction), [deallocate callback](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dumddi/nc-d3dumddi-pfnd3dddi_deallocatecb), and [D3D11 deferred destruction](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/changes-from-direct3d-10). Runtime resource handles must be passed intact to `pfnDeallocateCb`. Shared resources can retire during Flush; non-shared primaries require synchronous deallocation.
- Current UMD: `umd_resource_lifetime.c` drains queued retirements; `umd_runtime_device.c` calls `pfnDeallocateCb` and propagates its result; native `Flush` stage 3 reports only the final HRESULT. The queue guard and the runtime callback can both return `E_INVALIDARG`, so the current trace cannot assign ownership.

## Bounded diagnostic design
Add one failure-only receipt in `AdmissionUmdDeallocateResource`: stage 1 for local argument/callback guard, stage 2 for an HRESULT returned by the Windows runtime callback; include the full 64-bit runtime resource handle as two 32-bit words. Preserve the return value, callback timing, queue order, package capabilities, signer, GPU traffic and all firmware. The UMD owns this observation; Windows owns callback validation, KMD owns resource allocation objects, m1n1/Mu own only hardware/firmware. Test the real function with a failing callback and a null-handle guard, RED then GREEN; run the existing UMD contract test and full host suite before implementation commit.

## Hardware checkpoint and recovery
One package-only EXP959 run after exact958 Code43 cleanup and durable Code28 preflight. The new receipt must classify the first DWM Flush `E_INVALIDARG` as local guard or runtime callback and preserve the full handle; a DWM crash stack remains separately collected. If no error or no receipt in a bounded 750 s boot, verdict inconclusive. Copy/hash evidence to host before rollback. Recovery uses immutable ordinary GPU-visible profile, exact959 cleanup, ordered restart, durable Code28 preflight; never remove a live Code0 package. A classification result, not another DWM crash, is the smallest falsifiable checkpoint.

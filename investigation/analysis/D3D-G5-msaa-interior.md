# D3D-G5: fully covered MSAA pixels retain clear colour

## Boundary and observed evidence

EXP1292–EXP1298: the Windows D3D11 smoke draws two triangles into 2x/4x RGBA8/BGRA8, then resolves and reads back. Edge pixels mix colours, while fully covered interiors are `0xff000000`. EXP1294 repeated with lossless compression disabled. EXP1298 used `Texture2DMS.Load` and found **every** interior sample clear on x86 and ARM64; the AMD reference returned triangle colours. These are hardware observations supplied with this task, not deductions from source. The smoke's draw, clear, resolve and probe are at `drivers/apple-agx/windows/icd/agx_msaa_smoke.c:296-350` (prior to this diagnostic edit). The current source retains these operations below the iteration loop.

## Ranked causes

1. **Rasterizer multisample state is disabled in the D3D frontend.** Pinned Mesa `src/gallium/frontends/d3d10umd/Rasterizer.cpp:223` unconditionally sets `state.multisample = 0`, ignoring `MultisampleEnable`; the smoke requests TRUE (`drivers/apple-agx/windows/icd/agx_msaa_smoke.c:231`). The projection script has no replacement for that assignment (`drivers/apple-agx/mesa/scripts/build-native-asahi-state.py`, search `state.multisample`), whereas D3D blend SampleMask passes to `pipe->set_sample_mask` in pinned `OutputMerger.cpp:706-723`. Asahi gates API sample-mask handling on rasterizer `multisample` (`agx_state.c:2285-2303`). **HYPOTHESIS:** this disabled state makes the fully covered fast path omit colour writes while partially covered fragments still execute. The source proves the state mismatch, not the hardware consequence. If `mask1` and `mask5` behave exactly like `full`, that is consistent with this gate; a mask selecting only sample 0 or samples 0 and 2 contradicts it.

2. **Tilebuffer/EOT sample-count or geometry mismatch.** Asahi sizes tilebuffer storage by `sample_size_B * nr_samples` (`src/asahi/lib/agx_tilebuffer.c:87-105`) and selects the largest fitting tile (`:26-32`). For an 8-byte-aligned RGBA8 sample at 4x, 32 bytes/pixel does **not** fit a 32x32 tile under the 32767-byte limit (`:14,30`), so 32x16 is selected (`:31`). At 2x, 8 bytes/pixel fits 32x32. Asahi's framebuffer supplies sample count (`agx_state.c:3342-3350`) and PPP positions follow tilebuffer samples (`:3406-3408`). The Windows capture forwards `r->samples`, `r->sample_size_B`, utile dimensions and PPP control (`drivers/apple-agx/mesa/winsys/agx_win32_asahi_batch.c:430-433`); the G4 builder packs log2(samples), utile dimensions, tile blocks, PPP control and count (`drivers/apple-agx/shared/src/apple_agx_g4_builder.c:267-274,297-315`). The generated render template is patched at the G4 offsets, rather than supplying an independent sample count (`apple_agx_g4_builder.c:279-315`; `drivers/apple-agx/shared/src/apple_agx_render_template.generated.c`). **HYPOTHESIS:** a mismatch between captured dimensions/count and the actual tilebuffer or store path aliases full-coverage samples to clear. `full` failing throughout while `sampleindex` changes values per sample would narrow this to store/packing after shading. Compare 2x against 4x; a 4x-only failure points at the 32x16 transition.

3. **Background/clear overwrites fully covered results or EOT store loses them.** Asahi chooses BG_CLEAR only when the batch clear bit is set and no load is needed (`agx_state.c:3053-3095`), and EOT_STORE uses a PBE descriptor (`:3140-3158`). Its background shader marks MSAA sample shading and loads a sample ID (`src/asahi/lib/agx_bg_eot.c:70-86,125-132`); the EOT shader chooses an MS image when `nr_samples > 1` and emits an image store for each tilebuffer attachment (`:149-176`). Thus the source intends per-sample background and store. **HYPOTHESIS:** the projected clear or G4 background/EOT binding violates this intended contract. `copyinit` initializes the target by copying a blue MSAA texture cleared to a known pattern, then draws without clearing the target. Blue surviving at the centre means the draw did not write there; black appearing means a later background/clear or store operation overwrote it. Green at the centre excludes a clear-specific failure. The D3D clear path calls `pipe->clear_render_target` in pinned `OutputMerger.cpp:172-233`; projected clear handling is in `build-native-asahi-state.py:1524-1584`.

4. **API SampleMask is mishandled.** Pinned `OutputMerger.cpp:723` forwards the D3D value, and Asahi clamps it to four bits (`agx_state.c:858-869`) then to framebuffer samples (`:2285-2303`). Therefore default `0xffffffff` should become all enabled bits, then the prolog sentinel `0xff`, not an all-zero mask. This is lower-ranked because the source contradicts a simple 32-bit-versus-4-bit mask error. `mask1` should preserve draw colour only in sample 0; `mask5` only in samples 0 and 2 for 4x. If all remain clear, mask truncation alone is excluded. At 2x, mask5 selects only sample 0.

5. **Sample-frequency shading differs from pixel-frequency shading.** Asahi uses the fragment shader's sample-shading flag to set `nr_samples_shaded` (`agx_state.c:2305-2310`), and lowers sample masks in the shader path (`:1586-1598`). **HYPOTHESIS:** a pixel-frequency, fully covered path is faulty. `sampleindex` uses `SV_SampleIndex`; alternating green for even samples and red for odd samples at centre and edge would confirm per-sample writes and isolate the ordinary pixel-frequency path. If it too reads clear at centre, the defect is downstream or common to both paths.

The OpenGL ICD's `AGX_DBG_NOMSAA` path is explicit in `drivers/apple-agx/mesa/scripts/native-asahi-batch-lifecycle.py:597-601`; D3D sets `Backend.Multisample` at `drivers/apple-agx/mesa/winsys/agx_d3d10_windows.cpp:531`. It supplies no prior positive Windows MSAA render control. The pinned Mesa checkout and KMD are unchanged.

## Projected rasterizer correction (offline)

Microsoft's [D3D11_RASTERIZER_DESC remarks](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/ns-d3d11-d3d11_rasterizer_desc), [D3D10_RASTERIZER_DESC remarks](https://learn.microsoft.com/en-us/windows/win32/api/d3d10/ns-d3d10-d3d10_rasterizer_desc), and [D3D11.3 functional specification §3.5.2](https://microsoft.github.io/DirectX-Specs/d3d/archive/D3D11_3_FunctionalSpec.htm#352-warning-about-the-multisampleenable-state) say that for feature level 10.1 and later, `MultisampleEnable` selects the line algorithm and does not disable triangle MSAA. They explicitly distinguish FL 10.0: FALSE disables antialiasing for points, lines, and triangles even on a multisampled target. The pinned Gallium `src/gallium/include/pipe/p_state.h:117-128` declares `multisample`, `line_smooth`, and `line_rectangular` (the latter documented there as lines rasterized as rectangles or parallelograms); pinned `docs/gallium/cso/rasterizer.rst:135-137` defines `line_smooth` as line antialiasing.

The projection now overlays pinned `Rasterizer.cpp:217-239` through `drivers/apple-agx/mesa/scripts/build-native-asahi-state.py:1403-1420`: it enables `state.multisample` for 10.1/11 regardless of the descriptor flag, retains the descriptor flag for the 10.0 DDI, selects rectangular lines when enabled, and alpha-smoothed lines when disabled plus `AntialiasedLineEnable`. `CreateDevice` records whether `pCreateData->Interface` matches a D3D10.0 DDI version (`build-native-asahi-state.py:1127-1130`); the field is projected into `State.h` (`:896`). This classifies the **DDI interface**, not an independently reported feature level. **HYPOTHESIS:** the DDI 10.0 selection corresponds to the FL 10.0 path on this frontend; a D3D11 DDI running at FL 10.0 would need separate feature-level evidence.

Hardware confirmation still requires the smoke. After a package containing this correction, `full` should report green `0xff00ff00` at centre and edge in every sample. In 4x `mask1`, only sample 0 should become green, with samples 1–3 clear; in `mask5`, samples 0 and 2 should become green, with 1 and 3 clear. `sampleindex` should read green in samples 0/2 and red `0xff0000ff` in 1/3. `copyinit` should replace blue `0xffff0000` with green at the fully covered centre and edge. If `full` remains clear at the centre, the rasterizer state correction alone is rejected as the fix and the tile/EOT or background hypotheses remain. These are predicted patterns, not observed results.

## Offline diagnostic contract

Run `agx_msaa_smoke.exe out.txt 4 2 rgba <mode>` with `full`, `mask1`, `mask5`, `sampleindex`, or `copyinit` (also 2x and bgra). Each mode retains `SAMPLE` lines and adds `MODE ... centre ... edge ...` for every sample on first and last iterations. `full` draws one full-screen green triangle. `mask1`/`mask5` use D3D blend sample masks. `sampleindex` outputs green on even samples and red on odd samples. `copyinit` copies a blue, separately cleared MSAA texture into the target before drawing. Default arguments and the original `samples` mode retain their existing validation and output. These new modes are diagnostic: their final PASS reports completion/readback, not pixel correctness. Dry-run on the AMD adapter before interpreting Apple results.

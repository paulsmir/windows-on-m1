## Official WDDM requirements and status interpretation

Consulted 2026-09-28:

* [ResetFromTimeout](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmddi/nc-d3dkmddi-dxgkddi_resetfromtimeout): adapter reset must stop GPU memory access; returning failure causes bugcheck. A timeout commonly follows an unanswered preemption. P3 therefore describes failed recovery, not the initiating mechanism.
* [RestartFromTimeout](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmddi/nc-d3dkmddi-dxgkddi_restartfromtimeout): called after OS-side recovery/release, permits GPU access again; a trivial success can be valid when no extra work is needed. It cannot retroactively provide missing reset/quiesce guarantees.
* [ResetEngine](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmddi/nc-d3dkmddi-dxgkddi_resetengine): success requires completed reset, empty affected hardware queue, and readiness for new packets.
* [QueryDependentEngineGroup](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmddi/nc-d3dkmddi-dxgkddi_querydependentenginegroup): include every affected node, including the requested node; valid calls always succeed. The scheduler gives dependent preemption 500 ms before sequential engine-reset calls.
* [TDR in Windows 8 and later](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/tdr-changes-in-windows-8): per-engine support requires all three TDR DDIs and does not remove adapter-reset obligations. Failed engine reset escalates to adapter reset. Aborted-fence identity must stay within actual scheduler history; paging retries preserve original fence/order while render retries receive new fences.
* [PreemptCommand](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmddi/nc-d3dkmddi-dxgkddi_preemptcommand) and [GPU preemption](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/gpu-preemption): valid command acceptance returns success; already-completed work still needs synchronized preemption notification. Advertised granularity must reflect implementation. DMA-boundary support does not promise mid-command interruption or authorize a fabricated completed fence.
* [Interrupt types](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmddi/ne-d3dkmddi-_dxgk_interrupt_type) and [notification data](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmddi/ns-d3dkmddi-_dxgkargcb_notify_interrupt_data): DMA_COMPLETED names a completed submission; DMA_PREEMPTED supplies the preemption fence plus last actually completed submission. They are different notifications. Monitored-fence signal is also a distinct interrupt type.
* [Native GPU fence objects, existing monitored-fence section](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/native-gpu-fence-objects): existing monitored fences support CPU polling/blocking and GPU write plus notification; current-value updates must be atomic at 64 bits. This is explicitly described as an existing monitored-fence property, not a requirement invented from WDDM3.2 native wait functionality. [OpenSyncObjectFromNtHandle2](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmthk/ns-d3dkmthk-_d3dkmt_opensyncobjectfromnthandle2) ties storage width to No64BitAtomics and requires waiting for paging before using its GPU VA.

Microsoft's [SDK ntstatus.h](https://github.com/microsoft/win32metadata/blob/main/generation/WinSDK/RecompiledIdlHeaders/shared/ntstatus.h) line9836 defines `STATUS_DEVICE_HARDWARE_ERROR = 0xC0000483`. This symbolic status is a driver's reported failure category; it is not a measurement proving silicon malfunction.

## Deterministic source limitations; causal attribution stays open

**Active-private reset is intentionally unsupported.** `scheduler_windows.c:390–391` first calls `AdmissionGpuvaG3PrivateReset`. `gpuva_g3_windows.c:381–399` quarantines every Queued+Started private scene, poisons its process and returns false, explicitly because no GPU stop/TLB proof exists. The reset callback therefore returns `STATUS_DEVICE_HARDWARE_ERROR`. A second active-private branch at `scheduler_windows.c:401–413` also cancels uncertain work and returns that error. `ResetFromTimeout:491–497` delegates to this same ResetEngine path; `RestartFromTimeout:500–507` only checks scheduler initialization/fault state. Thus active-private TDR cannot currently claim recovered service. This is an explicit implementation gap behind advertised recovery capability, and returning failure is preferable to false success or freeing possibly DMA-live storage. The coordinating dump now supplies Queued+Started state, selecting this refusal predicate as detailed in R150-next-boundary.md; the source-only audit alone could not select it.

The nonprivate runtime reset path (`backend_platform_windows.c:3807–3895`) waits for workers, verifies the active packet, stops backend and rebuilds the owned firmware graph. Quiesce (`:1771–1786`) uses `AppleAgxRtkitSessionStop`, whose `shared/src/apple_agx_rtkit_session.c:311–363` sequence waits for AP and IOP power acknowledgements before clearing ASC run. It differs materially from Asahi's fault-mark/halt/resume path. Neither this sequence nor broker lease bookkeeping should be assumed to prove safe active-private UAT reclamation; the code explicitly refuses that inference.

**Deferred: monitored-fence atomic-publication gap, outside the proven boundary.** `gpuva_g3_paging_windows.c:585–587,634–643` creates an eight-byte monitored-fence paging record. `:754–763` writes it byte by byte and then executes a memory barrier. `lifecycle.c:647–650` zeroes the caps; no No64BitAtomics assignment is present. The source provides no atomic 64-bit publication guarantee; a final barrier does not make earlier byte stores atomic. This is a deterministic source-contract gap, with the exact package machine-code behavior still to inspect before calling an observed torn update. Any future regression should distinguish a rollover value with changing low/high bytes and verify one atomic publication, not merely final equality. This item is deferred: no extra fix or experiment belongs in R150, and no source edit/test/build for it was performed here. There is no evidence that this caused EXP864's preemption wait.

No `DXGK_INTERRUPT_MONITORED_FENCE_SIGNALED` is present in the inspected driver tree. Paging completion instead emits DMA_COMPLETED or DMA_FAULTED (`paging_windows.c:196–229`). Do not promote this absence alone to a defect: the exact OS CPU-paging completion semantics and waiter path must be established. A normal render DMA completion, a paging submission fence, and a monitored fence in memory remain separate identities.

## Capability and recovery recommendation

Keep capability advertisement unchanged for the minimal identity correction. Setting `SupportPerEngineTDR=0` would stop the per-engine recovery attempt; it does not suppress the mandatory adapter-wide ResetFromTimeout path or prevent 0x116 when that reset fails. The [Microsoft TDR contract](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/tdr-changes-in-windows-8) explicitly retains adapter-reset duties even for a driver implementing engine reset. Therefore a capability bypass cannot repair this failure, and neither reset success nor DMA/preemption completion may be fabricated to escape the watchdog.

The identity correction removes a deterministic failure before firmware publication. It does **not** make a true active GPU hardware TDR recoverable. General recovery still requires demonstrable quiescence: no future DMA, stopped/empty affected queues, safe UAT/TLB and lease disposition, valid fence accounting, and readiness before accepting new work. The current private reset refusal must remain fail-closed until those guarantees exist. Truthful caps/recovery qualification is a separate task; do not bundle it or the deferred fence-atomicity item with the proven owner correction.

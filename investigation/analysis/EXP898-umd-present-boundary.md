# EXP898: live DWM UMD Present admission discriminator

## Source-first observations

The exact package897 native frontend was generated from pinned `build-native-asahi-state.py` and the preserved builder output `native-Device.cpp` SHA `c85702c030f541100bd4db3cd0fab889dbfb51ddc1283c223b82f42f23a725c3`, `native-DxgiFns.cpp` SHA `026c9f5ae4306708eff69d57881a5da479770d2661b70b832d91bd3f728c256c`. `Device.cpp::CreateDevice` registers `_Present` and `_Blt` in the base DXGI table and returns `DXGI_STATUS_NO_REDIRECTION`; it does not register a `pfnPresent1` slot. The accepted interface switch only admits the D3D10_0/1 family. Pinned WDK26100 `d3d10umddi.h` has `IS_DXGI1_3_BASE_FUNCTIONS(Interface,Version)` gated by `Interface >= D3DWDDM1_3_DDI_INTERFACE_VERSION`; this native frontend's accepted interfaces do not satisfy it. Do not write a Present1 pointer into a smaller runtime table or claim it was negotiated without a measured interface/version. Official Microsoft [DXGI DDI support](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/supporting-the-dxgi-ddi) says a software-style UMD without hardware shared with its D3D9 DDI must return `DXGI_STATUS_NO_REDIRECTION`, and DXGI then should use another path that invokes `PresentDXGI`. Thus changing that return to `S_OK` is not justified by current evidence.

The native `_Present` path validates the DXGI arguments, then calls `AgxD3d10WindowsPresentationSubmit`, which flushes the native context, checks FlushStatus, then calls `AdmissionUmdSubmitPresent`; only the latter invokes `pfnPresentCb`. Native `_Blt` validates a strict full-screen identity transform before `AgxD3d10WindowsPresentationBlt` and its FlushStatus. The legacy `umd.c` path registers `AdmissionUmdPresent` and `AdmissionUmdPresent1`; both eventually call `AdmissionUmdSubmitPresent` if resource/callback/context guards pass. [Microsoft's DXGI presentation path](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/dxgi-presentation-path) distinguishes DWM-on shared-resource BltDXGI from DWM-off PresentDXGI, while [DXGI1_3_DDI_BASE_FUNCTIONS](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/dxgiddi/ns-dxgiddi-dxgi1_3_ddi_base_functions) adds Present1 only for a negotiated extended table. Classify these as FULL GRAPHICS UMD/KMD paths, not KMDOD.

Original EXP897 UMD log PID1216 (same PID as live DWM) contains no `_Present-entry`, `_Blt-entry`, `present-callback` or `g4-present-enter`, while KMD counters at +120/+300/+600 prove Present/virtual Present zero. This absence in UMD log is **not** a no-call proof: `AdmissionUmdDiagnostic` suppresses non-`reject-` records after 128 per process, and generated `_Present` entry/return use that bounded path. `_Blt` failures emit `reject-BltDXGI`, but successes have no durable per-call record. DWM PID1216 has two durable `reject-seterror fn=Flush line=540 hr=0x80070057` records. Exact native `Device.cpp:530-540` obtains that result from one of first QueryCollect, pipe flush/FlushStatus, FlushDeferredResources, or final QueryCollect, then calls SetError. The log does not identify which. The first KMD G3 copy-query failure receipt is predicate53/leaf-absent at GPUVA `0x20000`, 64 KiB with resident group available; its process/context is not yet causally tied to those DWM Flush returns. DWM later faults C0000005 in dwmcore expression evaluation, writer separate.

The smallest receipt-only change is bounded process-local UMD per-entry counts (first and power-of-two snapshots, plus first failure) for native `_Present`, `_Blt`, legacy `AdmissionUmdPresent`/`Present1`, native PresentationSubmit and `pfnPresentCb`, together with CreateDevice Interface/Version/table-capability/return and the exact failing Flush subcall. It must not set a new callback, alter `DXGI_STATUS_NO_REDIRECTION`, cap flags, Present arguments, driver behavior, firmware or ACPI. The trace-file mechanism is opt-in but the normal 128-record budget must not hide these bounded receipts.

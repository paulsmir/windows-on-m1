# R173 virtual BLT allocation-layout correction

## Source and evidence

EXP893's first Version2 receipt safely copied all96 bytes from the `DXGKARG_PRESENT` union pointer and probed raw offsets32/64 as live `ADMISSION_OPEN_ALLOCATION_MAGIC` objects (4/4 bytes each, NTSTATUS success). The observed source/destination `AllocationVirtualAddress` at offsets40/72 are `0x1050000`/`0xb0000`, and both 16-bit segment IDs are0. The KMD currently interprets that buffer as 24-byte `DXGK_ALLOCATIONLIST[1/2]`, reads handles at offsets24/48 as null, and returns `STATUS_INVALID_HANDLE`. The hardware result proves the actual WDDM3 virtual BLT payload is 32-byte `DXGK_PRESENTALLOCATIONINFO`-shaped for this path. This conflicts with [Microsoft's documented `DXGKARG_PRESENT` member description](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmddi/ns-d3dkmddi-_dxgkarg_present), which says `pAllocationList[1/2]` is driver-facing and `pAllocationInfo` is reserved. The pinned WDK26100 `d3dkmddi.h` defines both union forms and their exact layouts. Reproducible hardware observation takes precedence for this narrowly observed path; do not generalize to other Present modes/models.

Primary source files inspected: pinned `wdk26100-d3dkmddi.h` `DXGKARG_PRESENT`/both allocation structures and `DXGK_PRESENT_SOURCE_INDEX` constants; `present_windows.c` `AdmissionPresentOpen`/`AdmissionPresentBlt`/physical Patch; `callbacks.c` BLT route and trace; `allocation_windows.c` Open/Close allocation object ownership; `render_present.c` Version2 validation/copy; `gpuva_g3_windows.c` per-process graph; Asahi `drivers/gpu/drm/asahi/mmu.rs`; m1n1 `hv_agx_power_mmio.c` unchanged measurement; Mu R143 APPL0002 ACPI unchanged. EXP891 and EXP893 assisted/standalone contracts and ordinary/hidden recovery are recorded in `investigation/GPU_CURRENT_STATE.md`.

WINDOWS CONTRACT: the full WDDM3 virtual context has NoPatchingRequired; BLT source/destination open allocation objects and GPUVAs must be read from the actual 32-byte payload in this observed callback, validated with the same magic, owning-device, allocation-description and destination-write rules. The physical/nonvirtual Version1 Present and Patch path remains on the documented 24-byte list. AGX/ASAHI CONTRACT: once valid handles and GPUVAs are admitted, the existing graph-backed pagewise CPU copy and fence path remains unchanged; m1n1/DCP/Mu own no Windows allocation handle. TRANSLATION: normalize only virtual BLT source/destination from `DXGK_PRESENTALLOCATIONINFO[1/2]` into the existing admission and Version2 GPUVA command; use `AllocationVirtualAddress`, require segment0 and adapter index0, and never accept a null/foreign/read-only handle. WHAT IS STILL UNKNOWN: whether actual GPUVA source/destination graph ranges remain resident at submit, whether destination backs the DCP surface, and whether a different Present mode uses the documented 24-byte list. These are downstream or separate paths, not reasons to bypass handle validation.

ATOMIC CONTRACT: for the observed virtual BLT only, source/destination handle extraction, source/destination GPUVA extraction and segment/adapter fields all come from one 32-byte record stride. Mixing a handle from the 32-byte layout with VA or segment from the 24-byte layout is invalid. Supporting evidence is the pinned WDK layout plus EXP893's raw96B/magic/GPUVA receipt. Physical Version1 remains byte-equivalent. This is one independently observable Windows-facing ABI translation variable, not scheduler/UAT/power/DWM work.

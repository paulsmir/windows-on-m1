# EXP947: map the DWM render target to the DCP scanout surface

WHY THIS HYPOTHESIS:
1. In 944/945 the DWM process successfully submitted and completed render work, and its UMD Present callback returned S_OK; KMD `Present` and `VirtualPresent` stayed zero. The KMD first source-address receipt selected segment 2 / GPU address `0x1500110000`, resolved to local host PA `0x8e0110000`, which m1n1 observed DCP scanning. DWM's actual render source was a process GPUVA near `0x1f0000`; no evidence yet connects it to that physical surface.
2. m1n1's selected-surface snapshots at 944 120/300/600 seconds read all zeros while the last operator photo (941) showed fragments. CPU cache coherence limits a pixel conclusion, but physical identity can be compared without depending on sampled pixels.
3. EXP946 rejected a broad WrittenPrimaries change with `E_INVALIDARG`, so another capability or backbuffer flag probe is lower probability. The remaining direct discriminator is whether the completed DWM target and DCP-selected source name the same local pages or require a missing copy/flip.

WINDOWS CONTRACT: FULL GRAPHICS WDDM 3.0. Official Microsoft `DXGKARG_SETVIDPNSOURCEADDRESS` defines `PrimaryAddress` within `PrimarySegment` as the primary scanout surface, while WDDM GPUVA assigns process-specific virtual addresses to allocations. `DxgkDdiSubmitCommandVirtual` executes commands in that process context. These addresses cannot be equated without translation. The pinned WDK 26100 defines the DDI/segment types. This probe does not advertise or modify a capability.

AGX/ASAHI CONTRACT: The Asahi Apple DCP plane source `drivers/gpu/drm/apple/plane.c` (AsahiLinux/linux branch `asahi`, inspected 2026-10-03) describes BGRA scanout using explicit DMA address, width, height and stride. Current m1n1 `src/dcp_iomfb_present.c` constructs the J313 2560x1600/10240 BGRA surface; `src/hv_agx_power_mmio.c` confirms its latched IOVA and selected PA. Current Mu `J313AppleAgxAbiAdmission.asl.inc` exposes one APPL0002; ACPI and firmware state stay unchanged. KMD `gpuva_g3_windows.c` owns the locked CPU logical PTE graph; `AdmissionGpuvaG3FrameArmEscape` already receives DWM's process, context, allocation handle and canonical GPUVA without submitting a GPU job.

TRANSLATION: While holding the existing G3 state lock at a valid DWM FrameArm, read the existing logical PTE for that canonical GPUVA. After releasing the lock, persist one diagnostic binary receipt with the PTE's guest IPA, segment, allocation provenance, flags and mapping generation, plus the immutable selected source PA/address. This adds no page mapping, cache invalidation, DMA, queue, fence, render, present or DCP operation. Read it from the device registry on the same boot.

WHAT IS STILL UNKNOWN: Whether the DWM source PTE exists and matches the presented allocation; whether its local IPA equals the DCP-selected PA. A valid equal mapping excludes a missing copy/flip and moves investigation to pixel layout/coherence. A valid different mapping with no KMD Present/VirtualPresent identifies a missing transfer or address switch. A missing/mismatched PTE points to map lifetime. A single same-SDK 12-second stimulus after Code0 is enough; collect the receipt immediately and roll back exact EXP947 to normal GPU-visible Code28.

The last hardware-validated full profile (m1n1 EXP933 and Mu R143) and immutable normal recovery (m1n1 EXP377/Mu392) remain byte-identical. Original EXP946 evidence is host-gated and its rejected package has been removed. WHAT REAL BUG OR INVARIANT WILL THIS TEST CATCH? This is receipt-only hardware observation; an artificial RED test is not warranted. Existing G3 graph tests and zero-warning pinned ARM64 build/sign/hash/PDB gates must pass before hardware.

# One DWM frame: Windows Present to J313 scanout

This is a single offline pass over the full-graphics path. The reference frame is DWM PID1244 in EXP906: a 64 KiB render reference with kernel allocation `0xc0000a80` at GPUVA `0x7d0000` fails G3 COPY_QUERY. EXP906 then bugchecks at boot+82.918 s. EXP905 separately proves two DWM DXGI Present callbacks returned S_OK while the KMD Present counters remained zero through boot+823 s. Those are different boots and the audit does not merge their contexts or infer an ordering between them. The original EXP906 periodic snapshot and hidden dump/logs are tied by `EXP906-dwm-copy-query-tdr-verdict.md` and the host evidence manifest SHA `d7dd1e696190369a7ae57ecd56236faa8c3cd8c6d1fc2645573ab2fa837e4631`.

## Source and ownership

The inspected Windows source is `drivers/apple-agx/render-admission/umd/src/umd.c`, `umd_gpuva_windows.c`, `drivers/apple-agx/mesa/winsys/agx_win32_gpuva.c`, `agx_win32_gpuva_batch.c`, `agx_win32_asahi_scene.c`, the generated native `agx_pipe.c` in the pinned builder source archive, and its generator `drivers/apple-agx/mesa/scripts/native-asahi-batch-lifecycle.py`. The KMD path is `src/gpuva_g3_windows.c`, `src/gpuva_g3_paging_windows.c`, `src/present_windows.c`, `src/paging_windows.c`, `src/callbacks.c`, `src/display.c`, `src/scanout_windows.c`, `src/scheduler_windows.c`, and `drivers/apple-agx/shared/src/apple_agx_gpuva_g3_graph.c`. The hardware side is `m1n1_windows/src/hv_agx_retained_platform.c`, `hv_agx_scanout_service.c`, `hv_agx_scanout_broker.c`, `dcp_iomfb_present.c`, and the Mu R143 `J313AppleAgxAbiAdmission.asl.inc`/SSDT. This applies to **FULL GRAPHICS**. KMDOD display-only scheduler assumptions do not apply.

The Windows contracts are the pinned WDK26100 ABI and Microsoft's [WDDM operation flow](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/windows-vista-and-later-display-driver-model-operation-flow), [GPUVA and residency overview](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/residency-overview), [MakeResident callback](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dumddi/nc-d3dumddi-pfnd3dddi_makeresidentcb), [DXGI callback structure](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/dxgiddi/ns-dxgiddi-dxgiddicb_present), [KMD Present DDI](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmddi/nc-d3dkmddi-dxgkddi_present), [virtual submit arguments](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmddi/ns-d3dkmddi-_dxgkarg_submitcommandvirtual), and [TDR recovery](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/timeout-detection-and-recovery). Asahi's native batch/queue path and m1n1's retained UAT and DCP protocol define the AGX side. Mu exposes one APPL0002 device, reviewed local memory, and synthetic IRQ; it does not render, schedule Presents, or choose the DCP surface.

## Crash boundary

EXP906's preserved ARM64 MEMORY and minidump agree on `0x116 VIDEO_TDR_FAILURE` at uptime82.918 s, P3 `C0000483` (`STATUS_DEVICE_HARDWARE_ERROR`), with a System TDR-reset worker and AppleAgx KMD bucket. `scheduler_windows.c::AdmissionDdiResetFromTimeout` calls `AdmissionDdiResetEngine`; the private reset path can return that status. Neither header nor current receipt proves which packet/fence hung first, whether the private reset returned that code, or any causal link to the DWM query. Microsoft's TDR contract requires the driver to reset after a scheduler timeout; a new receipt must capture the outstanding packet context/fence and the reset substep/result without changing the reset behavior. DWM WER/writer remains separate.

## Deterministic fix and next receipts

**R185 is the only newly confirmed deterministic frame-path defect in this pass.** The test catches a real VidMM-to-AGX translation bug: all 4 KiB pages of a 64 KiB GPU-local allocation remain resident and owner-valid while an AGX 16 KiB leaf cannot be published. Historical KMD query rejects at predicate53; corrected QUERY and UPLOAD succeed into the expected scattered backing. Existing wrong-owner, offset, segment and local-range cases remain rejected. Focused R145 real-KMD replay, default G3 replay, Present trace and change-ledger tests passed. EXP906's exact DWM receipt proves the old predicate is live; a behavior-only package is still needed to validate the fix on hardware. No second deterministic defect is inferred from the adapter-global submit failure or TDR bucket.

The next passive receipts should use **one frame ticket**: UMD PID plus `KernelContext`, source allocation handle, canonical GPUVA and render fence. Each ring entry should be bounded and stamped with boot generation and monotonic sequence. At COPY_QUERY, record success/failure, predicate, first invalid resident page and published 16 KiB leaf state for that same context/allocation/VA. At UMD submit, record `pfnSubmitCommandCb` entry/HRESULT, fence signal/wait and terminal result; at KMD `SubmitCommandVirtual`, record branch/status, context, process generation, queued fence and completion DPC. Around `pfnPresentCb`, record the same context, source handle, opaque DXGI context, last completed render fence and callback HRESULT. At KMD Present entry/exit and Version2 worker, record source/destination open handle/GPUVA, rectangles, fence, copied bytes, destination local IPA/PA and completion or legal page fault. Capture the dxgkrnl Present/packet ETW event by context and fence because the OS queue itself cannot be instrumented by this driver. Finally compare KMD destination PA with m1n1's currently latched DCP swap ID, IOVA/PA and +120/+300/+600 pixel counts. A TDR receipt should persist outstanding context/fence, packet state and each reset substep/status. Never infer a per-DWM result from the adapter-global first G4 failure or a single early scanout snapshot.

**Smallest next checkpoint:** build R185 as the sole behavior change with the bounded receipts above, after their offline source/ABI tests and the full suite. Keep m1n1 EXP890 late-snapshot firmware and Mu R143 byte-identical. Preregister exact package/PDB/firmware hashes; one original >=750 s boot should either show same-context render completion followed by KMD Present and nonzero matched DCP surface, or name the next precise queue/fence/destination failure. Preserve the normal GPU-visible Code28/package0/autologon1 recovery and independent original/hidden host size/SHA gates before exact Code45 cleanup. A reset or missing late snapshot is a failed/inconclusive checkpoint, not a zero-Present proof. If implementing more than R185 uncovers another independent deterministic behavior change, verify it offline and keep the next hardware variable singular unless a pinned WDK invariant makes the changes atomic.

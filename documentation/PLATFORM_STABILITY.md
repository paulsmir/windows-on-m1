# J313 Platform Stability Checkpoint

## Current result

Windows 11 ARM64 boots from the internal NVMe namespace on all four efficiency and all four
performance cores. The physical panel, external USB input, networking, SSH, and RDP have all
worked on the development J313. The current checkpoint reduced early watchdog crashes and made
firmware startup markedly faster.

On 2026-08-13 the current eight-core candidate was accepted on the development J313 as the stable
development baseline for the next milestone. Windows reached the desktop, remained reachable over
SSH for more than twenty minutes, completed a bounded four-worker CPU load and repeated NVMe reads,
and produced no new bugcheck or platform/storage event during that session. The user also confirmed
that the interactive system was stable enough to proceed.

This acceptance means “known-good development baseline”, not “production release”. The stricter
Phase 0 gate in [ROADMAP.md](ROADMAP.md)—repeated cold boots and a sustained mixed workload—still
applies before a release can be described as generally freeze-free.

## 2026-08-13 debug checkpoint

The last captured long freeze is consistent with a specific EL2 invariant violation rather than
with framebuffer streaming. Timer injection continued on every guest CPU, but the runtime
`HCR_EL2` value was `0x324800400b9`: the `TWI` and `TWE` bits required by the diagnostic WFI/WFE
policy had been lost. The following rendezvous reached CPU0 only and reported CPUs 1 through 7
missing (`0xfe`). A Windows `CLOCK_WATCHDOG_TIMEOUT` dump independently named CPU1 as the hung
processor.

The accepted candidate makes the diagnostic WFI/WFE policy non-optional: every whole-register HCR
writer reapplies `TWI|TWE`, secondary entry applies the same policy, and a sparse runtime invariant
captures a lockless per-CPU snapshot if either bit is ever lost. More importantly, the normal
secondary fast path no longer consumes host rendezvous IPIs and no longer returns early while a
virtual interrupt is pending. vGIC `HCR.VI` recomputation was removed from the common exception
exit and retained only at the maintenance path that actually mutates list registers. This avoids
turning every trapped ICC access into a full LR scan and removes a cumulative DPC-latency source.

The build pipeline also now produces three distinct m1n1 roles. `m1n1-stage0.bin` and
`m1n1-stage1.bin` are packed only into `boot.bin`; `m1n1.macho` is rebuilt without either stage
macro and is the only artifact allowed for assisted chainload. This prevents a stage1 Mach-O from
being accidentally launched as the setup proxy.

The exact assisted artifacts used for the accepted run were:

```text
m1n1.macho  7b735bf12835ce8542e10710ac9a6280d759b53e93608362ebb44cb311956d40
J313_EFI.fd 0dba13c6fa652ec86900c8879babf6b48ac6a723f37f187ab99ee5f676e00ba5
boot.bin    594664eaeddf697b42dc69b61eae3b0278d050c199614ddebc081c3ef734d405
profile     display=both, debug=monitor
```

These hashes identify this hardware run; installers must still verify the manifest generated by
their own checkout instead of copying hashes from this document.

## Bounded overnight supervisor

For an unattended assisted diagnostic run, start the supervisor before cold-booting the target:

```sh
scripts/supervise-assisted.sh \
  --ssh-host TARGET_IP \
  --ssh-user WINDOWS_USER \
  --max-generations 3
```

It waits for exactly one protocol-responsive proxy, chainloads only the matching plain
`m1n1.macho`, starts the public launcher with the matching Mu firmware, and gives Windows four
minutes of boot grace. After Windows has become reachable, three consecutive SSH failures capture
two non-destructive SIGINT snapshots and classify the evidence; SSH loss alone never resets the
guest. Logs are kept under `.local/platform-stability/supervisor/`.

The generation count is intentionally bounded. The supervisor cannot recover a target whose USB
device still enumerates but whose proxy event loop no longer answers; at that point the SoC must be
cold-reset with the physical power button. No host program can manufacture a working command path
after both target endpoints have stopped consuming bytes.

## Checkpointed m1n1 work

The `m1n1_windows` checkpoint contains:

- safe fixed performance-state initialization for both T8103 clusters;
- a fast path for ordinary Windows breakpoint exception lowering;
- a dedicated NVMe fast path and lock so synchronous ANS I/O does not hold the global hypervisor
  lock for the complete operation;
- secondary-CPU fast handling for guest timer and local-interrupt FIQ work;
- reduction of the synthetic secondary EL2 tick from 5000 Hz to 100 Hz;
- manifest-controlled runtime diagnostics, including a quiet profile;
- lockless per-CPU watchdog snapshots and host tests for the new policy helpers.

Observed hardware evidence includes all eight CPUs entering and continuing to execute Windows, an
FIQ rate reduction from roughly 40,000/s to roughly 11,500/s, removal of the approximately 5,000/s
private synthetic tick, successful CPU/NVMe stress, and continued SSH liveness. Five older dumps
all contained `CLOCK_WATCHDOG_TIMEOUT` but named different hung CPUs (1, 2, 3, and 5), confirming
that the previous defect was systemic timer/IPI progress loss rather than one bad physical core.

The framebuffer transport also exposed an observer-only race: its checksum was calculated over
live guest pixels before the USB queue copied them. The guest could mutate a chunk between those
operations. The source now stages each chunk in stream-owned memory before checksumming/sending;
the regression test mutates the source during the callback and verifies that the transmitted
payload remains stable. This observer fix is host-tested and does not alter guest execution.

## Preserve the standalone baseline

Before an experiment, record the exact root, m1n1, and Mu commits plus the hashes of the installed
and candidate images. Store raw output below `.local/`, which is intentionally not published.

```sh
mkdir -p .local/platform-stability/baseline
git rev-parse HEAD
git -C m1n1_windows rev-parse HEAD
git -C mu rev-parse HEAD
python3 tools/artifact_manifest.py verify dist/j313/release/MANIFEST.json --profile release
```

On the target, keep the ESP backup created by `scripts/install-esp.sh inspect`. Do not overwrite the
only known-good recovery payload.

## Fast assisted iteration over USB

Assisted mode avoids rewriting the target ESP for each hypothesis. It requires another Apple
Silicon Mac only for development; normal standalone boot does not.

On the host, stop any previous launcher, connect the debug USB cable, and identify the two current
ACM endpoints:

```sh
cd /path/to/windows-on-m1
ls -l /dev/cu.usbmodem*
```

Build the candidate from the pinned root, m1n1, and Mu commits, then use one wrapper command to
chainload matching m1n1 and launch Mu/Windows:

```sh
scripts/run-windows.sh \
  --execution assisted \
  --display physical \
  --debug full \
  --chainload \
  --proxy /dev/cu.PROXY \
  --vuart /dev/cu.VUART
```

For independent framebuffer evidence, use `--display both` and start:

```sh
scripts/log-assisted.sh
scripts/display-assisted.sh
```

The log viewer is at `http://127.0.0.1:8765/`; the framebuffer viewer is at
`http://127.0.0.1:8766/`. Only one process may own the proxy and only one reader may consume a
given virtual-UART stream. A stale frame is not proof that Windows stopped.

For each run, record:

- root, m1n1, and Mu commit IDs;
- m1n1 Mach-O and Mu firmware SHA-256 values;
- launch profile and CPU count;
- start and end wall-clock times;
- physical UI, SSH/RDP, UART, per-CPU progress, timer, SGI/vGIC, storage, and bugcheck evidence;
- exactly one changed variable and whether the predicted counter changed.

Reboot the target back to its proxy payload between candidates and repeat the same wrapper. Do not
install a candidate on the ESP merely because it reaches the desktop once.

## Promote a candidate to standalone

An assisted result is only a hypothesis check. To ensure standalone receives the same fix:

1. Commit the m1n1/Mu/root source revisions used by the assisted run.
2. Update the root submodule pointers to those exact revisions.
3. Build `display=physical`, `debug=off` from the same tree.
4. Record the packed image hash and validate its manifest before installation.
5. Install it with `scripts/install-esp.sh`, cold boot without the host, and repeat the same workload.
6. Repeat with `debug=monitor` only if a standalone-only failure needs passive USB capture.

Example:

```sh
scripts/build-standalone.sh --display physical --debug off
python3 tools/artifact_manifest.py verify dist/j313/release/MANIFEST.json --profile release
sudo scripts/install-esp.sh install --disk diskXsY --image dist/j313/release/boot.bin
```

The candidate is complete only when assisted and standalone runs expose the same hardware contract,
diagnostics can be disabled without changing behavior, and the full Phase 0 acceptance gate passes.

## Regression gate while developing input

Apple Input work must preserve this baseline. Each firmware/ACPI/driver candidate must first prove
that all eight CPUs enter Windows, SSH remains responsive, and no new watchdog dump appears. Input
hardware is enabled only after its live ADT contract passes; a contract mismatch fails closed and
must not map or touch the controller. Any renewed pause is triaged with the same per-CPU timer,
SGI/vGIC, storage, and network evidence rather than hidden by disabling watchdogs or cores.

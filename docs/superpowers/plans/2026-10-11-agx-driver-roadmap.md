# План драйвера AppleAgx: OpenGL → 64-бит OpenGL → память и ANS → Direct3D

Дата: 2026-10-11. Ветка: `integration/ad04-windows-compiler`.

## Принципы

- Делаем настоящий драйвер: каждое временное решение заменяется документированным
  путём Windows/WDDM, а дефекты исправляются в том слое, который нарушает контракт
  (`AGENTS.md`, «Change discipline»).
- Перед изменением: живое состояние машины → Asahi → m1n1 → Mu/ACPI → документация
  Microsoft/WDK (порядок `AGENTS.md`).
- Каждый запуск на железе — по скиллу `agx-hardware-experiment`: гипотеза с
  доказательствами, одна переменная, записи BEFORE/ACTUAL, откат, `CHANGES.csv`.
- Стенд один (J313 + builder), поэтому все эксперименты на железе идут из этой
  сессии строго последовательно; параллельно можно вести только офлайн-работу.

## Где мы сейчас (EXP1209)

- CS 1.6, 2560×1600, на GPU. Без отрисовки оверлея Steam — ровные 60 Гц (vsync из
  `config.cfg`), с оверлеем ~43 fps (оверлей Steam под эмуляцией x86, EXP1208).
- Ошибок и отказов батчей в трассах нет; одна известная ошибка KMD (G1).

## Что сейчас сделано не «по-настоящему» и чем заменяется

| # | Сейчас | Должно быть | Шаг |
|---|---|---|---|
| 1 | Показ кадра: GPU-копия в staging, затем CPU читает 16 МБ из некэшируемой памяти и рисует через GDI (`SetDIBitsToDevice`) | `D3DKMTPresent` (Blt, `hWindow`) — документированный путь для OpenGL ICD; перенаправление в DWM делает dxgkrnl, blt выполняет KMD (`DxgkDdiPresent`) на GPU | G2 |
| 2 | Swap interval — сон по сетке на CPU | синхронизация показа с vblank средствами WDDM | G3 |
| 3 | Только 32-битный ICD; `OpenGLDriverName` указывает на несуществующий `AppleAgxOpenGL64.dll` | 64-битный ICD для ARM64 и x64-процессов | Этап 2 |
| 4 | `GL_VERSION 2.1`; отправка отклоняет MRT, MSAA, compute, часть форматов | GL 3.3+ с этими возможностями | G4 |
| 5 | KMD отказывает в повторной отправке вытесненной задачи → падает GL-контекст (EXP1197) | корректная повторная отправка по контракту WDDM | G1 |
| 6 | GPU-память — фиксированный резерв 1 ГиБ, вычтенный из RAM Windows; аллокации в системной памяти вешали GPU (EXP1026) | модель UMA: GPU работает с системной памятью через GPU MMU, резерв минимальный | M2 |

Не считаю временным решением кэшируемые «теневые» буферы для пулов и энкодера
(EXP1207): для эмулируемого x86-клиента это обычная техника — собирать команды в
кэшируемой памяти и копировать одним `memcpy`. Для нативных сборок (этап 2) её
нужно заново измерить и оставить, только если она даёт выигрыш.

## Этап 1. OpenGL (x86 ICD) правильным путём

**G1. Повторная отправка вытесненной задачи (KMD).** Это карточка, предложенная
раньше. Её делаю здесь, потому что ей нужен тот же стенд.
- Источники: документация WDDM по вытеснению и повторной отправке
  (`DxgkDdiPreemptCommand`, повторная отправка DMA-буферов после вытеснения);
  ветка 7 / subsite 0x201 `Wom1G4SubmitFailure` в KMD; EXP1197.
- Проверка: длинная сессия CS с принудительным вытеснением, ни одного падения контекста.

**G2. Показ через `D3DKMTPresent` (Blt).**
- Источники: [D3DKMTPresent](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmthk/nf-d3dkmthk-d3dkmtpresent)
  (пример для OpenGL ICD, правило «drainable context»),
  [D3DKMT_PRESENT](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmthk/ns-d3dkmthk-_d3dkmt_present),
  `present_windows.c` (как сейчас исполняется blt в KMD — на GPU или CPU),
  `stw_framebuffer.c` (что stw ждёт от winsys).
- Если blt в KMD выполняется на CPU, его нужно перевести на GPU (задание AGX).
  Это контракт KMD, его не обходят в ICD.
- После этого кольцо показа с CPU-копией и GDI удаляется.
- Проверка: оконный и полноэкранный режим, 100% показанных кадров, ноль CPU-копий,
  DWM работает, fps.

**G3. vsync через WDDM.** По документации выбрать механизм для blt-показа
(ожидание vblank от dxgkrnl / интервал показа). Сетку из EXP1209 оставить только
как запасной путь, если механизм WDDM недоступен. Полноэкранный flip — позже,
отдельным шагом.

**G4. Возможности GL 3.3+.** MRT, MSAA, нужные форматы, затем compute (GL 4.3)
в пути отправки G4; поднять `GL_VERSION`. Тесты — подмножество piglit
(конформанс).

**G5. Надёжность.** Потеря устройства и TDR (`STATUS_GRAPHICS_GPU_EXCEPTION_ON_DEVICE`
→ пересоздание контекста), несколько контекстов и окон, ресайз, Alt-Tab, решение
по glthread.

**Готово, когда:** CS 1.6 показывает все кадры без CPU-копии; час игры без сбоев;
подмножество piglit проходит.

## Этап 2. 64-битный OpenGL

- `AppleAgxOpenGL64.dll` собирается как ARM64X (ARM64 + ARM64EC). Так его загрузят
  и нативные ARM64-приложения, и x64-игры под эмуляцией: в x64-процессе код
  драйвера выполняется нативно, эмулируется только игра.
  Источник: [Arm64X PE](https://learn.microsoft.com/windows/arm/arm64x-pe) —
  бинарники в System32 собираются как ARM64X, чтобы их загружали и x64-, и ARM64-процессы.
  До сборки проверить, что x64-`opengl32` на ARM64 берёт `OpenGLDriverName` и
  принимает ARM64X.
- Собрать closure Mesa и ICD для ARM64 и ARM64EC (clang-cl); мост D3DKMT без WOW64.
- Тестовая игра. Твои CS и Portal 2 под Windows не 64-битные OpenGL:
  - CS 1.6 / CZ — 32-битный OpenGL;
  - CS: Source и Portal 2 — D3D9;
  - CS2 — D3D11/Vulkan.
  
  Для x64 OpenGL предлагаю **Xonotic**: бесплатный, x64, OpenGL 2.x + GLSL, есть
  `timedemo`, свой «паркур» записывается через `record` — тот же приём, что с CS.
  Установить его нужно тебе. CS 1.6 остаётся регрессией для x86.
- **Готово, когда:** Xonotic timedemo идёт на GPU (`GL_RENDERER` Apple, без
  программного GDI Generic); смоук-тест нативного ARM64 проходит.

## Этап 3. Память: почему Windows видит 4.2 ГБ из 8

Факты (карта RAM гостя из реестра, 2026-10-11, и `hv_autonomous_layout.generated.h`):

| Диапазон | Размер | Что это |
|---|---|---|
| 0x800000000–0x850000000 | 1.25 ГиБ | ниже `phys_base` гостя: хост m1n1 и резервы iBoot |
| 0x860000000–0x8A0000000 | 1 ГиБ | окно ramdisk (`ramdisk_max_size`), резервируется в каждой загрузке, даже без ramdisk |
| 0x8E0000000–0x920000000 | 1 ГиБ | фиксированный локальный резерв GPU (`AGX_LOCAL_RESERVE_V2`), отдан устройству как память |
| 0x9DF708000–0xA00000000 | ~0.5 ГиБ | резервы Apple в верхней части RAM |
| остальное | 4.22 ГиБ | RAM Windows (сюда входит 1 ГиБ, отображённый в младшие адреса гостя) |

«Гибкой» память пока не стала. GPU-аллокации в системной памяти вешали GPU
(EXP1026), поэтому всё, что использует GPU, живёт в фиксированном резерве 1 ГиБ.
На обычных ПК встроенная графика берёт системную память динамически через GPU MMU,
и Windows видит почти всю RAM.

- **M1.** Окно ramdisk резервировать только при загрузке с ramdisk (WinPE/ANS).
  Это m1n1 и Mu, даёт +1 ГиБ. Для ANS001 окно должно оставаться доступным.
- **M2.** Модель UMA: исправить в KMD зависание при системной памяти (EXP1026), GPU
  выделяет память из системной через GpuMmu, локальный резерв сжать до нужд
  прошивки и scanout. Даёт ещё ~1 ГиБ, и GPU перестаёт быть ограничен 1 ГиБ.
- **M3.** По живому ADT и карте iBoot разобрать 1.25 ГиБ ниже `phys_base` и вернуть
  то, что не нужно хосту.
- **Готово, когда:** Windows видит ≥ ~6.2 ГиБ (оценка, подтвердить замером), GPU
  выделяет больше 1 ГиБ при нагрузке.

## Этап 4. ANS (нативный NVMe)

Продолжаем по плану из прошлой сессии (`.worktrees/ans-native`, `ANS_CURRENT_STATE.md`):
1. ANS001 на запечатанном комплекте с обновлённым путём отката (обычный
   GPU-visible профиль и `recover.sh`) — проверка передачи владения и `APPL0003`
   с Code 28.
2. Офлайн-блокер DART: полный учёт унаследованных таблиц DART (DCP, дисплей,
   PIODMA, xHCI, `pt-region-*`), регрессионные тесты.
3. Перебазировать m1n1 и Mu на текущую ветку, затем лестница ANS002–ANS005
   (QUERY/CLAIM → контроллер и admin-очередь → Identify → чтение со сверкой хешей),
   потом запись на тестовый раздел и загрузка Windows через AppleAns.

Нужны твои решения (из того плана): когда Air свободен от GPU-экспериментов, флешка
для логов, делать ли отдельный скилл `ans-lab`.

# EXP778 VidMm page-table CPU visibility

## Boundary and source contract

EXP778 package779 accepted the paging SystemContext (`Flags=5`, node0, affinity1, IRQL0) and then Windows bugchecked `VIDEO_MEMORY_MANAGEMENT_INTERNAL 0x10E`, subtype `0x49`. The symbolized stack enters `dxgmms2!VIDMM_PAGE_TABLE_BASE::GetCpuVisibleAddress` from `GetDriverUpdateAddress` during `InitPagingProcessVaSpace`, before any KMD UpdatePageTable call. Dump: `.local/experiments/EXP778-addadapter-context/hardware-evidence/092426-12843-01.dmp`, SHA256 `cc6e68c34a48b3eeb07bebc56eca5385f54877f22d295eb9459de5f19ebf0e01`.

Pinned WDK 26100 `d3dkmddi.h:2720-2744,11102-11125` defines `DXGK_SEGMENTDESCRIPTOR4/5::CpuTranslatedAddress`. [DXGK_SEGMENTDESCRIPTOR4](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmddi/ns-d3dkmddi-_dxgk_segmentdescriptor4) distinguishes GPU `BaseAddress` from CPU physical `CpuTranslatedAddress`; the correction preserves GPU base `0x1500000000` and publishes the guest IPA separately. [DXGK_SEGMENTFLAGS](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmddi/ns-d3dkmddi-_dxgk_segmentflags) says `CpuVisible` means CPU access at this physical address. [GPU segments](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/gpu-segments) describes direct CPU mapping of a visible memory segment. [GPU virtual address](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/gpu-virtual-address) says VidMm allocates page tables in `PageTableSegmentId`; our caps put both normal and paging-process tables in local segment2. [CPU host aperture](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/cpu-host-aperature) says page-table bootstrap needs CPU mapping when a segment is not directly visible.

Our QUERYSEGMENT4/5 reported segment2 with `CpuVisible=0`, `CpuTranslatedAddress=0`, and no CPU host aperture. The local segment is backed by `DxgkCbCreatePhysicalMemoryObject(CONTIGUOUS_MEMORY)` plus `DxgkCbAllocateAdl(RequireContiguous=1)` in `physical_memory_windows.c`; `DxgkCbMapPhysicalMemory` supplies its CPU VA. `AdmissionMemoryRuntimeScanoutView` computes the aligned guest IPA for the same local object. The m1n1 broker still owns AGX host PA/UAT translation; Windows VidMm needs the guest CPU physical address for mapping. No m1n1/Mu/Asahi path changes are proposed.

## Correction and checkpoint

A portable validator requires the exact reportable local range, live CPU mapping, contiguous ADL-backed guest IPA, 64-KB alignment, matching GPU segment base, and nonzero host address. G3 QUERYSEGMENT4/5 set `CpuVisible=1` and `CpuTranslatedAddress=GuestIpaAddress` only when the validator passes; other profiles retain their declarations. The runtime view now checks ADL contiguity and range containment. Host test RED on old code and GREEN on the correction. Package780 WDK ARM64 build must pass before one new cold-boot discriminator. Expected checkpoint: no 0x10E/0x49, first UpdatePageTable or a named later failure. Recovery: immutable GPU-hidden exact-package removal and ordinary Code28 on SSH loss/bugcheck.

The physical memory object is mapped noncached. This change does not advertise a cached segment or alter per-allocation `Cached`/`CpuVisible` flags, so it does not claim CPU/GPU cache coherency or broaden the UMD Lock contract. The segment is a linear CPU mapping of its contiguous guest IPA range, as required for VidMm page-table bootstrap.

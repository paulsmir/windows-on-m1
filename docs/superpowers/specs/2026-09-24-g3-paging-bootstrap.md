# EXP779 paging-process UpdatePageTable bootstrap

EXP779 package780 advanced past CPU page-table mapping, but WER then recorded `0x10E (0xB, ..., 0xC000000D, ...)`. CDB identifies `dxgmms2!VIDMM_GLOBAL::CompleteBuildPagingBufferIteration` during `UpdatePageTableInvalidate` in `InitPagingProcessVaSpace`. Microsoft [bugcheck 0x10E](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/bug-check-0x10e---video-memory-management-internal) defines subtype 0xB as an invalid KMD error code from `BuildPagingBuffer`. Dump `.local/experiments/EXP779-cpu-visible/hardware-evidence/092426-16296-01.dmp` SHA256 `fcb73c05c2ffcc0a71b1c08a7f1f5f1fecc8faa3069d3a8a9101727f23677892`.

Pinned WDK 26100 `d3dkmddi.h` and Microsoft [UpdatePageTable](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmddi/ns-d3dkmddi-_dxgk_buildpagingbuffer_updatepagetable) say paging-process initialization always uses CPU_VIRTUAL mode with `pDmaBuffer=NULL` and must complete immediately. [Update flags](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmddi/ns-d3dkmddi-_dxgk_updatepagetableflags) define `Repeat`: one PTE is replicated across all requested entries. [System paging process](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/system-paging-process) confirms the immediate CPU bootstrap path. Existing KMD accepts CPU_VIRTUAL at its outer gate but then assumes VidMm's CpuVirtual pointer lies inside the KMD's separate mapping. It also vetoes Repeat and would index beyond a single PTE if the veto were removed. The actual first UpdatePageTable flags were not recorded in EXP779, so these are documented contradictions, not yet a measured cause of C000000D.

Correct both input contracts together: translate VidMm's nonpaged CpuVirtual pointer with `MmGetPhysicalAddress` to guest IPA, require it to lie inside the validated contiguous local segment, and use the same synchronous G3 graph/broker update. Select PTE index zero for Repeat in parent and leaf paths. Before every UpdatePageTable, persist mode, flags, span, pointer presence and raw table address; flush a result status after return. Host RED→GREEN covers Repeat indexing and source gates. Pinned WDK26100 ARM64 build gates a separate hardware discriminator. Its checkpoint is successful first paging update or an exact input/result receipt and named later failure. No caps, m1n1, Mu, signer, or recovery changes are made.

The 16-KB table span validator permits a table exactly at `segment end − 0x4000` and rejects one byte beyond, the end address, and underflow before reading its tail physical address. [DxgkDdiBuildPagingBuffer](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmddi/nc-d3dkmddi-dxgkddi_buildpagingbuffer) runs at PASSIVE_LEVEL and documents only `STATUS_SUCCESS`, `STATUS_GRAPHICS_ALLOCATION_BUSY`, and `STATUS_GRAPHICS_INSUFFICIENT_DMA_BUFFER`. The input receipt calls `ZwFlushKey` before the operation; the result receipt does so after. A malformed input, invalid table mapping, or poisoned broker has no truthful busy/DMA-shortage interpretation, so the driver deliberately fails closed with its actual NTSTATUS. VidMm may bugcheck; the durable receipts and dump identify the cause without silently treating a failed page-table update as successful.

## EXP780 observed correction

EXP780's flushed receipt resolves the exact remaining `C000000D` guard: Windows 26100 sent the first CPU_VIRTUAL `UpdatePageTable` with `Repeat|InitialUpdate`, 8192 entries and non-NULL DMA/private pointers (4096 bytes each). This differs from Learn's usual `pDmaBuffer=NULL` description for paging-process initialization. The KMD's explicit pointer-presence veto rejected the request before any table update. The next package removes only that veto. CPU_VIRTUAL still updates immediately through the synchronous graph/broker path and does not write or advance the DMA pointers.
